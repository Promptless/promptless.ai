## Overview

A GitHub PR trigger starts documentation work from pull request activity in the repositories you monitor. Choose whether Promptless runs when a PR opens, gets its first approval, merges, or receives new commits. To ask for documentation on one PR, [mention `@promptless` in it](#request-documentation-from-a-pull-request).

When an event matches your trigger, Promptless reads the full pull request. That includes the title and description, the code diff, review comments, and every commit, including commits added after the PR opened. When a reviewer requests changes, Promptless reads both the feedback and the commits that address it. If the change needs a documentation update, Promptless creates documentation suggestions.

<Aside type="note">
  Promptless processes PR information in real time and doesn't store it. It analyzes a PR only when a configured trigger event or an `@promptless` mention starts work on it.
</Aside>

<Aside type="tip">
  You can also ask Promptless in Slack or Microsoft Teams to set up the trigger for you. For example, "@Promptless add a GitHub PR trigger for my acme/api repo that only runs on the src/ directory." See [Ask Promptless to update your configuration](/docs/for-docs/get-the-most-out/ask-promptless-to-update-config).
</Aside>

## Before you start

- An admin role in your Promptless organization, to connect GitHub and edit the [Configuration page](https://app.gopromptless.ai/configuration).
- The GitHub organization that holds the repositories you want to monitor, connected to Promptless. Promptless can't save a GitHub PR trigger until it is. If the organization isn't connected yet, [connect it](#connect-github) first.

## Add a PR trigger

<Steps>
  1. On the [Configuration page](https://app.gopromptless.ai/configuration), switch to **YAML** mode.

  2. In the `triggers` section, add a `github_pr` trigger with a match clause for the repositories you want to monitor:

     ```yaml
     triggers:
       my-pr-trigger:
         trigger_type: github_pr
         match:
           - repos:
               - acme/backend
               - acme/frontend
             trigger_on:
               - opened           # When PR opens
               - first_approval   # After first approval
               - merge            # When PR merges
             trigger_directories:
               - src/
     ```

  3. Save the configuration.
</Steps>

Each match clause takes these fields:

| Field                 | Required | Description                                                                                                                                                                      |
| --------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `repos`               | Yes      | The repositories to monitor, in `owner/repo` format, or the literal `all`. A clause that lists `updated` needs an explicit list.                                                 |
| `trigger_on`          | Yes      | One or more [trigger modes](#choose-trigger-modes): `opened`, `first_approval`, `merge`, or `updated`.                                                                           |
| `trigger_directories` | No       | Only PRs that change files in these directories trigger documentation updates. See [Limit a trigger to specific directories](#limit-a-trigger-to-specific-directories).          |
| `repo_topics`         | No       | Only repositories with at least one of these GitHub topics trigger documentation updates. See [Limit a trigger to tagged repositories](#limit-a-trigger-to-tagged-repositories). |

A trigger runs when any of its match clauses matches. For every field, including repository exclusions and the base-branch and owner filters, see the [Configuration Reference](/docs/for-docs/reference/configuration-reference#triggers).

To catch up on pull requests that opened or merged before you configured the trigger, run a [backfill](/docs/for-docs/connect/triggers#backfill-suggestions) from the saved trigger. Before you go live, review the first batch of backfilled suggestions to calibrate Promptless with your documentation style.

### Choose trigger modes

List one or more trigger modes in each match clause's `trigger_on`:

| Mode           | `trigger_on` value | When Promptless runs             | Choose it when                                                                                                                  |
| -------------- | ------------------ | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Opened         | `opened`           | Once, when the PR opens          | You want documentation suggestions ready alongside the code changes, so reviewers can evaluate both.                            |
| First approval | `first_approval`   | Once, on the PR's first approval | You want documentation work to start after code review, so Promptless analyzes the reviewed changes.                            |
| Merge          | `merge`            | Once, when the PR merges         | You want documentation only for changes that have landed.                                                                       |
| Updated        | `updated`          | On every push to an open PR      | You want an open PR re-reviewed as it changes. See [Re-review open PRs on every push](#re-review-open-prs-on-every-push) first. |

The first-approval mode triggers once per PR, on the first approval. Later approvals, including re-approvals after requested changes, don't trigger more documentation updates.

## Re-review open PRs on every push

The `updated` mode re-reviews an open pull request each time someone pushes new commits to it. Promptless's suggestions then stay current as the PR changes. It's available for GitHub PR triggers only, and pushes start no work unless a match clause lists `updated` in `trigger_on`.

Each push starts a new review, so a PR with many incremental commits gets many reviews. Scope the clause tightly: name an explicit `repos` list, and narrow it further with `trigger_directories`.

<Aside type="caution">
  A match clause that lists `updated` in `trigger_on` must name an explicit `repos` list; it cannot use `repos: all`. Other clauses in the same trigger are unaffected.
</Aside>

Promptless skips pushes to draft PRs and to PRs that Promptless opened. A push from any other contributor, including an external or first-time contributor, starts a new review. On a push, an `@promptless` mention in the title or description doesn't bypass these filters or start a review.

To turn `updated` on, add it to a clause's `trigger_on` list. That clause must name an explicit `repos` list:

```diff
 triggers:
   my-pr-trigger:
     trigger_type: github_pr
     match:
       - repos:
           - acme/backend
           - acme/frontend
         trigger_on:
           - opened           # When PR opens
           - first_approval   # After first approval
           - merge            # When PR merges
+          - updated          # Re-review on each new push
         trigger_directories:
           - src/
```

To re-review on each push without the other modes, give `updated` its own clause with an explicit `repos` list, scoped with `trigger_directories`:

```yaml
triggers:
  docs-review-bot:
    trigger_type: github_pr
    match:
      - repos:
          - acme/docs
        trigger_on:
          - updated          # Re-review on each new push
        trigger_directories:
          - docs/
```

The explicit-`repos` requirement applies to each match clause, not to the whole trigger. One trigger can pair a `repos: all` clause for the other modes with a scoped `updated` clause:

```yaml
triggers:
  my-pr-trigger:
    trigger_type: github_pr
    match:
      - repos: all           # broad clause for one-time modes
        trigger_on:
          - opened
          - merge
      - repos:               # scoped clause required for updated
          - acme/docs
        trigger_on:
          - updated
        trigger_directories:
          - docs/
```

## Limit which pull requests trigger a review

Promptless checks each pull request event against these rules before it starts a review:

| Pull request                                                                                                                                             | What Promptless does                                                                                                              |
| -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| A draft PR                                                                                                                                               | Skips it until it's marked ready for review. An `@promptless` mention in the title, description, or a comment still starts work.  |
| A PR that Promptless opened                                                                                                                              | Skips it.                                                                                                                         |
| A PR that changes only dot-directories, such as `.github/`, `.circleci/`, or `.beads/`, or root-level dot-files, such as `.gitignore` or `.editorconfig` | Skips it. These files are usually CI and tooling configuration. A PR that also changes other files gets a normal review.          |
| A PR with no changes in the clause's `trigger_directories`                                                                                               | Skips it, unless another clause matches. See [Limit a trigger to specific directories](#limit-a-trigger-to-specific-directories). |
| A PR in a repository without any of the clause's `repo_topics`                                                                                           | Skips it, unless another clause matches. See [Limit a trigger to tagged repositories](#limit-a-trigger-to-tagged-repositories).   |

To narrow a trigger further, add a directory or topic filter.

### Limit a trigger to specific directories

Limit a trigger to pull requests that change files in specific directories, such as `src/` or `api/`. Use it to focus documentation updates on the parts of your codebase your docs cover. In YAML, set the clause's `trigger_directories` list. To set it in the dashboard:

<Steps>
  1. On the [Configuration page](https://app.gopromptless.ai/configuration), select the **Triggers** tab.

  2. Expand an existing **GitHub pull requests** trigger, or create one.

  3. Open **More filters (optional)**.

  4. Select **Only when files in these folders change**.

  5. Enter each folder path, and press Enter or type a comma after each one.

  6. Select **Save changes**, or **Add trigger** for a new trigger.
</Steps>

<img src="https://promptless-customer-doc-assets.s3.us-east-2.amazonaws.com/docs-images/org_3DaVKUzHgjyjaODgCPaDmjXezqp/github-directory-trigger-9b64b800.png" alt="A GitHub pull requests trigger on the Configuration page, with More filters expanded and docs/ entered under Only when files in these folders change" />

Promptless then considers only PRs that change files in those directories, and ignores changes to other files.

### Limit a trigger to tagged repositories

If you have many repositories and only some need documentation automation, use [GitHub topics](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics) to choose which ones trigger Promptless. Promptless triggers on any repository that has at least one of the topics you configure. In YAML, set the clause's `repo_topics` list. To set it up in GitHub and the dashboard:

<Steps>
  1. In GitHub, add a topic, such as `docs-watch` or `promptless`, to each repository you want Promptless to monitor.

  2. On the **Triggers** tab of the [Configuration page](https://app.gopromptless.ai/configuration), expand a **GitHub pull requests** trigger, or create one.

  3. Open **More filters (optional)**.

  4. Select **Only repos tagged with these GitHub topics**, and enter the topics.

  5. Select **Save changes**, or **Add trigger** for a new trigger.
</Steps>

To add a repository to the trigger later, tag it with a configured topic in GitHub. To remove one, remove the topic from the repository.

## Set how Promptless publishes suggestions

Set how Promptless publishes suggestions from PR triggers in your [publishing policies](/docs/for-docs/reference/configuration-reference#policies):

| Option                | Policy setting                           | Effect                                                                                                                                               |
| --------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Source PR comments    | `publishing.suppress_source_pr_comments` | Posts a summary comment on the source PR that links to the documentation suggestions, so reviewers see them while reviewing the code. On by default. |
| Automatic PR creation | `publishing.auto_create_pr`              | Opens a PR in your documentation repository with the suggested changes.                                                                              |

Slack notifications are separate from source PR comments. Promptless sends them to the channel in your `notification.slack_channel` policy setting, whether or not source PR comments are on.

### Suppress source PR comments

Set `suppress_source_pr_comments: true` to stop comments on source PRs. Promptless still creates documentation suggestions.

```yaml
policies:
  default:
    publishing:
      suppress_source_pr_comments: true
```

Teams commonly suppress comments:

- During pilot or onboarding periods, before Promptless has been introduced to the broader engineering team
- On public repositories, while keeping comments enabled for private repos

## Request documentation from a pull request

To ask for documentation work on a specific pull request, mention `@promptless` or `@promptless-for-oss` in it. Matching is case-insensitive, and the repository needs the GitHub integration installed. A direct mention is a request, so it works outside your trigger modes. Where you put the mention decides when Promptless responds:

| Mention location                           | When Promptless responds                                                                     |
| ------------------------------------------ | -------------------------------------------------------------------------------------------- |
| PR title or description                    | When the PR opens, reopens, or is marked ready for review, or when an edit adds the mention. |
| PR comment                                 | When the comment is posted, on an open, draft, merged, or closed PR.                         |
| PR review summary or inline review comment | When the review is submitted.                                                                |

When you mention `@promptless` in a PR title, description, comment, or review, Promptless adds a 👀 reaction so you know it saw your request. The reaction shows up even when Promptless decides no documentation change is needed, so a missing suggestion doesn't mean your mention was ignored.

### Request documentation via PR title or description

A mention in a PR's title or description makes Promptless review the PR whatever your trigger configuration says. If your trigger runs only on first approval, the mention starts a review as soon as the PR opens. If the PR targets your documentation repository, which is normally outside your source scope, the mention pulls it in anyway.

Include the mention anywhere in the title or description:

```markdown
## Summary

Added new authentication endpoints for SSO integration.

@promptless please document these API changes
```

A mention left in a merged PR's description doesn't start another review when the PR merges.

### Request documentation via PR comments

Tag Promptless in a comment on a source PR to request documentation work:

```text
@promptless please update the docs for this API change
```

A comment mention helps when:

- A PR was created before your trigger was set up
- You want documentation for a PR that's already merged or closed
- The automatic trigger didn't activate for your PR
- You want to provide specific instructions about what to document

Promptless ignores comments that don't mention it directly.

### Request documentation via PR reviews

Mention `@promptless` in the summary body of a submitted PR review, or in any of its inline review comments. Promptless treats either as a direct request and reviews the PR. A mention in the summary body gets the 👀 reaction on the review. A mention that appears only in an inline comment gets the reaction on that comment.

### Trigger from automated accounts

A direct `@promptless` mention doesn't have to come from a person. It takes priority over Promptless's bot filter. A comment or review from an automated account, like a GitHub Actions workflow, triggers documentation work just as a teammate's does. Build docs requests into your CI by having an Action post an `@promptless` comment whenever you want docs updated or reviewed.

For example, a GitHub Actions step can comment on a pull request to ask Promptless to document the change:

```yaml
- name: Ask Promptless for docs
  run: gh pr comment "$PR_NUMBER" --body "@promptless please update the docs for this change"
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    PR_NUMBER: ${{ github.event.pull_request.number }}
```

Mentions work from any automated account, including CI or review Actions that run checks like Doc Detective or snippet validation. Promptless still ignores bot comments and reviews that don't mention it. When Promptless acts on an automated account's mention, its reply names the mention as the reason. The account's owner can then decide whether to keep tagging it.
