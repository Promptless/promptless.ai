## Overview

Start a Promptless session from a Jira ticket. When the work is done, Promptless replies on the ticket and links the documentation PR. Use Jira triggers when your team plans and tracks documentation work in Jira.

A ticket starts a session in one of four ways:

| Path               | What starts a session                                                                                     | What it needs                           |
| ------------------ | --------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| Label              | Adding a label whose first token is `promptless`, such as `promptless` or `promptless-urgent`.            | Atlassian connected.                    |
| Mention            | @mentioning the account Promptless acts as in a comment.                                                  | An attached Atlassian service account.  |
| Assignment         | Assigning the issue to the account Promptless acts as.                                                    | An attached Atlassian service account.  |
| Configured trigger | Creating an issue, adding a label, or changing an issue's status, when it matches a Jira trigger you add. | Atlassian connected and a Jira trigger. |

The label, mention, and assignment paths are built in and need no YAML configuration. A configured trigger starts sessions whether or not a service account is attached.

Two related capabilities work differently. [Jira as a context source](/docs/for-docs/connect/context-sources/jira) lets Promptless read tickets for background without acting on them or writing back. To have Promptless create a Jira issue, see [Create a Jira issue on request](/docs/for-docs/reference/integrations/atlassian#create-a-jira-issue-on-request).

## Before you start

- Atlassian connected to Promptless. Every path needs it. If it isn't connected yet, [connect it](#connect-atlassian) first.
- For the mention and assignment paths, an [attached Atlassian service account](#attach-a-service-account-for-mentions-and-assignments).
- To add configured Jira triggers, an [organization admin](/docs/for-docs/reference/configuration-reference#permissions-and-conflict-detection) role.

## Connect Atlassian

Connecting Atlassian turns on the built-in label path and lets you add configured Jira triggers.

## How a Jira ticket starts a session

To start a session from a ticket on a built-in path, do one of the following:

- Add a label whose first token is `promptless`. The label path works whenever Atlassian is connected.
- With a service account attached, @mention the account Promptless acts as in a comment. Promptless matches the mention by the account's ID. A mention picked from Jira's autocomplete shows the account's display name, so the comment needs no literal `@promptless` text.
- With a service account attached, assign the issue to the account Promptless acts as.

Without a service account, a mention or an assignment starts no session.

Labels whose first token is `promptless` are reserved for the built-in label path, and they never route to a configured Jira trigger.

The three built-in paths share one built-in trigger, `jira_mention`. To set publishing or notifications for them, target `jira_mention` in a policy rule. Each path has no key of its own.

When one Jira update carries more than one built-in path, Promptless starts at most one session, for the highest-precedence path that applies:

- A `promptless` label starts a session even when a mention or assignment on the same update starts none.
- Assignment outranks the label. With a service account attached, an update that both assigns the issue and adds a `promptless` label starts the session as the assignment.

### Reply on the ticket

Promptless answers on the ticket and attaches the documentation PR as a remote link, a linked reference on the Jira issue. Re-posting never adds a duplicate link. Promptless also flags the ticket for follow-up if it goes unanswered, the same way it tracks an unanswered Slack thread.

With a service account attached, Promptless comments as the service account. Without one, its comments, new issues, and links appear as the person who connected Atlassian. Promptless posts them only with explicit permission in your Knowledge Base or the current request.

## Add a configured Jira trigger

Add a configured Jira trigger to start sessions when an issue is created, gets a label, or changes status in the projects you choose.

1. On the [Configuration page](https://app.gopromptless.ai/configuration), switch to **YAML** mode.

2. In the `triggers` section, add one or more Jira triggers. Each `trigger_type` names the moment it activates on:

   ```yaml
   triggers:
     jira-new-docs-issue:
       trigger_type: jira_new_issue
       match:
         - project_key: [DOCS]
     jira-needs-docs-label:
       trigger_type: jira_label_added
       match:
         - new_label: [needs-docs]
     jira-ready-for-docs:
       trigger_type: jira_status_change
       match:
         - is_done: true
         - new_status: ["In Review", "Pull Request"]
   ```

3. Select **Save**.

You can also add these triggers on the **Triggers** tab. Under **Tasks & tickets**, select **A new Jira issue**, **A Jira label**, or **A Jira status**.

The trigger map keys, such as `jira-new-docs-issue`, are yours to name. The `trigger_type` values, such as `jira_new_issue`, are fixed type identifiers. See the [Configuration Reference](/docs/for-docs/reference/configuration-reference#triggers) for the full schema.

### How a configured trigger activates

Each trigger type names the edge an issue crosses: the issue being created, a label being added, or the status changing. A trigger activates once per crossing. A later update about an issue that still matches doesn't activate it again. For example, editing the description of a `DOCS` issue doesn't re-activate a new-issue trigger. Commenting on an issue that already carries `needs-docs` doesn't re-activate a label trigger.

Creating an issue crosses every edge at once, because the issue arrives with its labels and its status. A new `DOCS` issue filed with `needs-docs` matches both `jira-new-docs-issue` and `jira-needs-docs-label`, and Promptless starts one session tagged with both keys.

Within one `match` clause (each `-` item), the fields are ANDed. Separate clauses are ORed. So `jira-ready-for-docs` above activates when an issue reaches any done status, and separately when it reaches `In Review` or `Pull Request`. All Jira fields match case-insensitively.

Multi-value matches compare each value on its own. A second listed label activates the trigger even when the issue already holds the first, and a move between two listed statuses activates it again.

### Scoping to projects

`project_key` is required on `jira_new_issue`, which would otherwise activate on every issue created anywhere in the site. It's optional on the other two types. Set it unless you mean the whole site: as written, `jira-needs-docs-label` above matches a `needs-docs` label in any project. A `jira_status_change` clause can hold `project_key` alone, which matches any status change within those projects.

### Labels

A `new_label` that lists a label whose first token is `promptless` never matches, because the built-in label path claims those labels first. Name the label something else, such as `needs-docs`. A label that only contains the word, such as `docs-promptless` or `not-promptless`, isn't reserved.

### Matching done statuses

`new_status` names statuses one by one. Status names differ by project, anyone can rename them, and a done status added later isn't covered. `is_done: true` matches Jira's done status category, which stays stable across projects and renames, so one clause covers every done status your site has.

`is_done` accepts only `true`. To act on statuses outside the done category, name them with `new_status`.

<Aside type="note">
  An issue moved between two done statuses, such as `Shipped` to `Closed`, activates an `is_done: true` trigger again. The move is a second status change into a done status, so it crosses the trigger's edge a second time.
</Aside>

### Instructions and output

`instructions` is optional on all three Jira trigger types. It holds standing work that Promptless runs each time the trigger activates. Use it to give a label a standing job: apply the label, and Promptless runs those instructions against the issue. Omit `instructions` to work from the issue alone. A blank value is invalid.

```yaml
triggers:
  jira-docs-plan:
    trigger_type: jira_label_added
    instructions: Scope the docs impact, do not publish.
    match:
      - new_label: [docs-plan]
        project_key: [DOCS]
```

A Jira trigger's output goes wherever the run's `escalation` and publishing settings send it. That's a docs suggestion and PR, plus the usual Slack or Teams notification. As on the built-in paths, Promptless also [replies on the ticket](#reply-on-the-ticket) and flags it for follow-up if it goes unanswered. A blocker or escalation from the run comments on the ticket and notifies any configured `escalation` channel.

## Attach a service account for mentions and assignments

Attach a dedicated Atlassian service account to give Promptless its own identity in Jira. Promptless then posts as that account, and the mention and assignment paths start sessions.

Without a service account, the account Promptless acts as is the real person who connected Atlassian. Promptless can't tell ordinary ticket traffic for that colleague from a request for Promptless, so mentions and assignments do nothing. Promptless drops the update, doesn't reply on the ticket, and doesn't notify you in Slack or Teams. Only the label path and configured triggers start sessions, and they read the ticket as the connecting account.

Before you attach one, an Atlassian admin creates the service account's credentials with the scopes it needs. See [Atlassian service account](/docs/for-docs/reference/integrations/atlassian#atlassian-service-account).

1. On the [Integrations page](https://app.gopromptless.ai/integrations), go to the Atlassian card.
2. Enter the service account's **Client ID** and **Client secret**.
3. Select **Attach**.

The card then lists the attached account's details. A **Not working** or **Unconfirmed** badge on the service account section flags a problem to fix.

Promptless ignores its own activity in Jira. It recognizes its own updates by the service account when one is attached, and by the connecting account otherwise.

## Example

A team adds the `jira-docs-plan` trigger above. A writer adds the `docs-plan` label to ticket `DOCS-204` in the `DOCS` project, which activates the trigger. Following its standing instructions, "Scope the docs impact, do not publish," Promptless analyzes the linked change and scopes which documentation it affects. Promptless then comments on the ticket with that scope. The run doesn't publish, so there's no PR to link.

Later, the team moves `DOCS-204` into `In Review`. That status change activates `jira-ready-for-docs`, which watches for the `In Review` and `Pull Request` statuses. When someone files a new `DOCS` issue that already carries `needs-docs`, the issue crosses the new-issue edge and the label edge at once. It matches both `jira-new-docs-issue` and `jira-needs-docs-label`, and Promptless starts one session tagged with both keys.

The team has also attached a service account. An engineer @mentions the account Promptless acts as on `DOCS-204` to ask for the update. Promptless replies on the ticket and attaches the documentation PR as a remote link.
