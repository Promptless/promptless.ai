This example teaches Promptless to clean up the documentation for a retired feature or integration. It deletes the pages, redirects their old URLs, and records the removal in the changelog. It's an example of pairing a written workflow with a trigger, as described in [Teach Promptless a custom task](/docs/for-docs/get-the-most-out/teach-promptless-a-custom-task). The [review inbound documentation PRs](/docs/for-docs/get-the-most-out/teach-promptless-a-custom-task/review-inbound-doc-prs) example pairs a workflow with a GitHub PR trigger. The [weekly analytics doc-gaps](/docs/for-docs/get-the-most-out/teach-promptless-a-custom-task/analytics-docs-gaps) example pairs one with a schedule trigger. This one pairs a removal workflow with a Slack trigger, because a retirement is usually a human decision announced in a channel. The steps below write the workflow, configure the trigger, then save the workflow, hook, and trigger.

## What a clean removal covers

A removal is one documentation change with three parts, and the workflow keeps them together:

- **The pages come out.** The retired page and every reference to it leave the docs.
- **The old URLs still resolve.** Each removed URL redirects somewhere useful, so a bookmark or search result doesn't dead-end.
- **The change is on the record.** The changelog gains a removal entry, while the original announcement stays as history.

## Prerequisites

Before you set up this task, make sure you have:

- **The Slack integration connected**, with the Promptless bot invited to the channel where your team announces retirements (for example, `#docs`).
- **The GitHub integration connected** to your documentation repository, so Promptless can open the removal as a documentation PR.
- **The ability to chat with Promptless** in Slack or Teams to make edits for you, or **admin access** to edit the Knowledge Base directly.

## Set up the task

Set up the task in three steps: write the workflow, configure the trigger, then save the workflow, hook, and trigger.

<Steps>
  1. **Write the workflow.** The workflow captures *how* to remove a retired feature's docs. It covers what to delete, where to redirect, and how to record the change. Write the workflow *body* as a markdown file under `doc_workflows/` in your Knowledge Base (for example, `doc_workflows/deprecate-and-remove-docs.md`). Give it contents like this:

     ```markdown
     # Deprecate and remove documentation

     When a feature or integration is retired and its user-facing documentation
     has to come out:

     1. Delete the pages outright. Remove the page file itself and every
        reference to it — its entries in overviews, lists, tables, card grids,
        and navigation, plus any inline mentions on other pages. Do not move the
        page to an archive directory or hide it behind a flag. Git history keeps
        the source, so a deletion is always recoverable. A deletion that leaves a
        dangling link or an orphaned mention is not finished. Leave build
        artifacts such as the route manifest and Open Graph images to the
        `prebuild` step in CI.

     2. Add the redirects by hand. `src/lib/generated/redirects.json` is
        hand-maintained — no script writes it — so add a redirect entry for each
        deleted URL, and its `.md` variant, in the same change. Point each
        redirect at the replacement page when the retired thing has one (an
        individual integration page redirects to the integrations index), or at a
        short retired-notice page when it has none. Never point a removal redirect
        at the site homepage; a homepage redirect reads as a soft 404 and tells
        the reader nothing about what happened to the page they wanted.

     3. Keep the changelog history and add a removal entry. Leave the dated entry
        that originally announced the feature exactly as it is — it records what
        shipped at the time. Add a separate, current-month `**Deprecated:**` entry
        that announces the removal and points readers to the replacement or to
        help, following the existing changelog style. Fold that entry into this
        removal's own suggestion; do not open a standalone changelog suggestion
        for it.

     4. Stop at the documentation collection. A removal here stays here. Do not
        chase references to the retired thing into other repositories as part of
        the removal.
     ```

     Then add an explicit "If, then" hook in `PROMPTLESS.md` that points to this workflow, so it fires reliably (`PROMPTLESS.md` is always loaded into the agent's instructions, whereas the workflow file is loaded on demand):

     ```text
     If someone announces in #docs that a feature or integration is retired, then follow the removal workflow in `doc_workflows/deprecate-and-remove-docs.md`.
     ```

     Alternatively, define the workflow as an Agent Skill living in a doc collection, like under `.claude/skills/deprecate-and-remove-docs/SKILL.md` in `acme/docs`. In that case the `PROMPTLESS.md` hook must name that doc collection and skill:

     ```text
     If someone announces in #docs that a feature or integration is retired, then use the `deprecate-and-remove-docs` skill from `acme/docs`.
     ```

  2. **Configure the trigger.** Add a Slack trigger that activates when your team announces a retirement in a channel. Create it in the dashboard: in the left sidebar, open **Settings** and select **Configuration**, open the **Triggers** tab, and choose **Add a trigger**. Build the trigger in the **Form** view (the default); the **YAML** view shows the underlying `promptless.yaml`. The trigger listens to the channel where retirements are announced, and looks like this in YAML:

     ```yaml
     triggers:
       deprecate-and-remove-docs:
         trigger_type: slack_listen
         match:
           - channels:
               - docs
     ```

     Channel names don't need the `#` prefix, and the Promptless bot has to be invited to any channel you monitor. The hook you added in Step 1 narrows a monitored channel down to retirement announcements. Promptless acts on "we've retired the Bitbucket integration" and leaves ordinary chatter alone. See [Slack message triggers](/docs/for-docs/connect/triggers/slack-messages) for the full behavior of a `slack_listen` trigger.

  3. **Save the workflow, hook, and trigger.** The trigger is saved from the Configuration page in Step 2. Save the workflow file (`doc_workflows/deprecate-and-remove-docs.md` or the Agent Skill) and the "If, then" hook in `PROMPTLESS.md` from the Agent Knowledge Base. There are two ways to do this:

     - An organization admin edits the files directly in the [Agent Knowledge Base](/docs/for-docs/get-the-most-out/agent-knowledge-base) (in the left sidebar, open **Settings** and select **Agent Knowledge Base**).
     - You can ask Promptless to make these changes for you. It edits `PROMPTLESS.md`, the workflow file, and `promptless.yaml` then commits the change.
</Steps>

## What Promptless does on each removal

Say your team retires the Bitbucket integration and posts that in `#docs`. Promptless:

1. Recognizes the retirement announcement and opens a documentation PR for the removal.
2. Deletes the Bitbucket integration page and clears its references from the integrations index, any comparison tables, and inline mentions elsewhere.
3. Adds the redirect entries by hand, pointing the old Bitbucket URL and its `.md` variant at the integrations index.
4. Adds a current-month `**Deprecated:**` changelog entry for the removal, leaves the original Bitbucket announcement in place, and folds the entry into the same suggestion.

The removal lands as a single suggestion and documentation PR you review before it merges. Set a notification channel to see what each run produced, and an escalation channel to catch a broken integration or access problem. See [Notifications](/docs/for-docs/tune/notifications) for how to route suggestion and problem alerts separately.
