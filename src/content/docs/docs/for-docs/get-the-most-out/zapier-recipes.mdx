Every recipe on this page has the same shape. A system outside your docs repository learns something new — about the product, the market, or a buyer — and a **Zap** forwards that signal into Promptless through the **Submit Documentation Task** action. The Zap in Zapier carries the signal; Promptless does the research and writing, then opens one pull request for you to review. You say what changed and where, and Promptless writes the edit itself — drafting the page when none exists yet and updating it when it does, so a recipe works even before you have a persona profile or comparison page.

The Promptless integration for Zapier also exposes triggers, actions, and searches of its own, but this page is about what to build, not a field-by-field reference. You'll see each trigger's and action's fields when you add the Promptless app in Zapier's editor. For the request that backs the **Submit Documentation Task** action, see [API triggers](/docs/for-docs/connect/triggers/api).

## Keep buyer persona profiles current from call recordings

Sales and discovery calls are where you hear how buyers actually talk. This recipe turns each recorded call into an update to the persona profiles your docs already carry.

<Steps>
  1. **Start the Zap from a new meeting transcript.** Use your call recorder as the trigger app — Grain, Fathom, Gong, Zoom, or any recorder with a Zapier trigger for new transcripts.

  2. **Filter to sales and discovery calls (optional).** Add a filter step so only customer-facing calls continue and an internal standup doesn't start the rest of the Zap. Without it, a standup transcript could trigger a needless persona-profile update.

  3. **Add the Submit Documentation Task action.** In **What Changed**, tell Promptless to update the buyer persona profiles it maintains in your docs: the objections prospects raised, the words they use for the problem, the alternatives they compared against, and the outcomes they said they cared about.
</Steps>

The persona profiles are what Promptless reads when it writes persuasive marketing pages, so keeping them current makes those pages speak in the buyer's own language — which is what generates more marketing-qualified leads.

In **Supporting Context**, add one label and value pair per detail you want a reviewer to see: a call-date label set to the date of the call, an account label set to the account name, and a recording label set to the link to the recording. With those attached, a reviewer of the resulting pull request can trace a persona claim back to the call it came from.

## Keep comparison pages honest by watching competitors

Comparison pages go stale the moment a competitor ships. This recipe checks on a schedule and asks Promptless to rewrite the pages that a change affects.

<Steps>
  1. **Run the Zap on a two-week cadence.** Start it from **Schedule by Zapier** so it runs on a fixed interval rather than waiting on an event.

  2. **Scrape the pages you watch.** Add a step that reads the competitor pages you watch — a page-monitoring or scraping app from Zapier's app directory, or Webhooks by Zapier pointed at a scraping service you run.

  3. **Add the Submit Documentation Task action.** In **What Changed**, ask Promptless to rewrite the "us versus them" comparison pages the scraped changes affect, and pass the scraped material through **Supporting Context**, along with the scraped page's URL and the date you scraped it, so a reviewer can trace a comparison claim back to the source page and when it was captured.
</Steps>

The constraint that makes this work: hand Promptless the scraped material and let it decide what is actually new and worth documenting, rather than trying to diff pages inside the Zap. Promptless opens a pull request only when there's an actual documentable change, so a scrape that finds nothing new produces no pull request. Two weeks is a starting interval you can tune. **Schedule by Zapier** and the web-scraping step are Zapier's own building blocks. The Zap gathers and forwards; Promptless judges and writes.

<Aside type="caution">
  A comparison claim about a competitor is the kind of change worth reading closely before it merges. Review these pull requests by hand rather than auto-merging them.
</Aside>

## More recipes to build

The same shape fits any system that learns something your docs should reflect:

- **A new support ticket theme.** When your helpdesk surfaces a recurring theme across support tickets, forward it to the **Submit Documentation Task** action to close the docs gap the tickets keep exposing.
- **A closed-won deal in your CRM.** When a deal moves to closed-won in your CRM, prompt Promptless to refresh the case study or proof point that the win backs up.
- **A published release note.** When you publish a product release note, forward it so Promptless refreshes the marketing pages that describe the capability it covers.

## Scope your Zaps so they stay useful

- **Target a Doc Collection when the recipe always touches the same docs.** Set the **Doc Collection** in the action — a collection is [how Promptless learns your docs](/docs/for-docs/connect/doc-locations/how-promptless-learns-your-docs) — when a recipe always lands in the same set. While you're piloting a recipe, target a single collection and widen later; [run a pilot](/docs/for-docs/start-here/run-a-pilot) to prove it out before broad rollout. If you leave it blank, Promptless picks the collection itself, so a task can land as a pull request against a collection you didn't expect — which is what to check when reviewing.
- **Say what changed.** Put enough detail in **What Changed** that Promptless doesn't have to guess what changed or where. A vague instruction like "update the docs" leaves Promptless guessing, while naming the persona profile or comparison page and what changed about it gets a focused pull request.
- **Expect a pull request per task.** Each task opens one pull request for you to review before any change lands.
