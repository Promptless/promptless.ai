## Overview

Readers come to your docs to get something done, such as setting up a deploy or turning on single sign-on. Many ask an AI assistant to work it out from your docs for them. Docs evals test whether your docs carry them through. For each doc collection, you keep a set of reader tasks. Each task has success criteria that say what a correct response has to tell the reader to do. Promptless drafts the tasks from your critical user journeys. A model you pick works out each task from your docs alone, and a judge model grades its response against the success criteria.

The results show which tasks your docs support, which success criteria each response missed and why, and which pages the model read. When a task fails, Promptless can open a docs task to fix the gap. A trend table shows how each task scores across models, modes, and runs, so you can see whether a docs change fixed it.

Docs evals aren't open to every organization yet, so the dashboard navigation doesn't list them. To try docs evals, [contact the Promptless team](/docs/for-docs/reference/getting-help).

Docs evals live on the [**Docs evals**](https://app.gopromptless.ai/content-strategy/docs-evals) page of the dashboard. Select the collection to work on from **Doc collection** at the top of the page.

## Before you start

- An admin role in your Promptless organization to draft, add, and edit tasks and to start runs. Other members can view tasks, runs, and results, and can export tasks.
- Critical user journeys that cover the collection, to draft tasks from. They're on the [**Critical User Journeys**](https://app.gopromptless.ai/content-strategy/journeys) page in the Content Strategy area.
- A verified model provider key. Runs use your organization's own keys, and only models whose provider has passed a test call appear in the run options. See [Add your own model provider keys](/docs/for-docs/audit/model-provider-keys).

## Draft tasks from your journeys

Each critical user journey says what starts a reader on a job, what success looks like, and the steps and pages in between. Promptless turns each journey into a draft task for you to review and edit.

- On the **Docs evals** page, select **Draft tasks from your journeys**.

Promptless drafts one task for each journey that covers the collection and has no task yet. Each draft has:

- A task written the way a reader would ask an AI assistant for help, from the journey's starting situation and goal
- One success criterion for each essential step of the journey, including steps the journey marks as a gap in your docs
- Up to four expected pages, taken from the journey's steps
- The journey's name as its display name, and the journey's ID as its slug

A step that the journey marks as a gap still gets a success criterion, so the gap fails the task. Drafts are enabled, so the next run attempts them. Drafting uses Promptless's own model, not your model provider keys.

A draft is only as specific as its journey, and journeys rarely name exact commands, settings, or values. Edit each draft before you run it, and add those details to its success criteria, because the judge can check only what a criterion states.

Draft again after you add journeys. Promptless skips each journey that already has a task whose slug is the journey's ID. Drafting again never overwrites a task you edited. To draft a journey's task again from the start, delete its task first.

## Add or edit a task

Add a task yourself for a job that no journey covers, or edit a draft.

<Steps>
  1. On the **Docs evals** page, select **Add task**, or select **Edit** on a task's row.

  2. Enter a **Display name** and a **Slug** of lowercase letters and digits joined by single hyphens, up to 64 characters. Trends and the YAML export name the task by its slug. Keep the slug of a drafted task, or drafting again adds a second task for its journey.

  3. Under **Task**, enter what the reader is trying to get done, the way they would ask an AI assistant for help.

  4. Under **Success criteria**, add each thing a correct response has to tell the reader to do. The judge grades the response against every criterion. A task needs at least one.

  5. Optional. Under **Expected pages**, add part of the URL or path of each page the model should read, such as `configuration-reference`.

  6. Select **Save task**.
</Steps>

Runs attempt only tasks that are **Enabled**. Clear **Enabled** on a task to keep it out of runs without deleting it.

## Start a run

A run attempts every enabled task once with one model in one mode, then grades each response.

<Steps>
  1. Under **Start a run**, select the **Model** that attempts the tasks. Each option shows its price per million input and output tokens.

  2. Under **Mode**, select how the model reads your docs:
     - **HTTP** reads your published docs site, the way a reader or an AI assistant does. The collection needs a `docs_root_url` in its [configuration](/docs/for-docs/reference/configuration-reference).
     - **Raw docs** reads the docs repository with a read-only shell, without the published site.

  3. Optional. Under **Judge model**, select a different model to grade the responses. By default, the run's own model grades them.

  4. Optional. Clear **Open a docs task for each reader task the docs failed** if you only want the results.

  5. Read the cost summary, then select **Start run**.
</Steps>

Each attempt is capped at $2.00 and each grade at $0.50, and your provider keys pay for both. The run appears under **Runs** as **Queued**, then **Running**. The page refreshes the run while it works. To stop an unfinished run, select **Cancel** on its row.

A collection has one unfinished run at a time. To start another, wait for the current run to end or cancel it. A run attempts five tasks at a time and must finish within six hours, so it can attempt up to 45 enabled tasks. With more enabled, the run doesn't start. Clear **Enabled** on some tasks and run them separately.

## Read the results

Select **Results** on a run's row to see one row per task. The results header names the model that judged the responses.

A task passes when the response meets every success criterion and the model read every expected page. A success criterion isn't met when the response leaves it out, contradicts it, hedges it, or gets its command, setting, or value wrong. A response that says your docs don't cover a step also misses that step's criterion. A page counts only when the model opened it during the run. A URL the response cites without reading it doesn't count.

| Verdict     | Meaning                                                                             |
| ----------- | ----------------------------------------------------------------------------------- |
| **Pass**    | The response meets every success criterion, and the model read every expected page. |
| **Fail**    | The response missed at least one success criterion or expected page.                |
| **Error**   | The task couldn't be attempted or graded.                                           |
| **Stopped** | The run ended before this task finished.                                            |

Each result also shows:

| Column                 | What it shows                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------- |
| **Unmet expectations** | Each missed success criterion with the judge's reason, then each expected page the model didn't read. |
| **Pages visited**      | The pages or files the model read.                                                                    |
| **Cost**               | What attempting and grading the task cost.                                                            |
| **Docs task**          | A link to the docs task Promptless opened to fix the gap.                                             |

When a failed task's docs task from an earlier run is still open, the run reuses that docs task. The result marks its **Docs task** link as reused from an earlier run.

A failed result also shows the suggested fixes from its docs task, with links to their docs PRs.

## Track tasks across runs

The **Trends** table has one row per task and one column per run, newest first, grouped by model and mode. Each mark shows a run's verdict for the task. Hover a mark to see what the task cost in that run. Trends appear once a run finishes.

Compare columns to see whether a docs change fixed a failing task, or whether a cheaper model or the other mode does as well.

## Export tasks

Select **Export YAML** to download the collection's tasks. Each task becomes one case with these keys:

| Key            | Value                   |
| -------------- | ----------------------- |
| `id`           | The task's slug         |
| `display_name` | The task's display name |
| `enabled`      | Whether runs attempt it |
| `question`     | The task text           |
| `expect`       | The success criteria    |
| `expect_urls`  | The expected pages      |
