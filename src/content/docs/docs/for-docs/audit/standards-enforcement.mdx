[Vale](https://vale.sh/) is an open-source prose linter that enforces style rules across documentation. When Vale is configured for a doc collection, Promptless lints prose before creating suggestions, catching style violations before they reach your review queue.

<Aside type="note">
  Vale is one of the tools behind [Audit and keep your docs healthy](/docs/for-docs/audit/keep-docs-healthy). It holds restandardized pages on-style so legacy content doesn't drift again after you fix it.
</Aside>

## What Promptless does

When Vale is enabled, Promptless:

- Downloads external style packages your config references when those styles aren't already vendored in your repository.
- Lints every prose file it creates or substantially edits.
- Fixes findings according to your config's `MinAlertLevel`. When you set an alert level, Promptless fixes every finding Vale reports. When it's unset, Promptless treats error-severity violations as blocking and fixes them before creating the suggestion.

This keeps suggestions aligned with your style guide from the start, reducing back-and-forth during review.

## Setup

Vale is enabled automatically when Promptless detects a Vale configuration file in your docs repository.

### Automatic detection

During doc collection setup, Promptless scans the collection for a Vale configuration file matching any of the five names Vale recognizes: `.vale`, `_vale`, `vale.ini`, `.vale.ini`, or `_vale.ini`. When Promptless finds one, Vale linting activates automatically using that config. When the scan finds more than one candidate, Promptless uses the config in the shallowest directory within the collection's scope. It breaks ties by the filename order above.

### Manual configuration

You can also set the Vale config path manually:

1. Open the Promptless dashboard.
2. Go to your doc collection.
3. Click the edit button.
4. Under **Vale config**, enter the repo-relative path to your Vale configuration file (e.g., `.vale.ini` or `docs/.vale.ini`).

<Aside type="note">
  If your Vale config references external style packages (like Microsoft, Google, or write-good), Promptless downloads them automatically. This happens the first time it lints during a session.
</Aside>

## How it works

Promptless runs Vale after drafting prose content:

1. **Sync packages** - Downloads any external style packages your config references.
2. **Lint prose** - Runs Vale on created or edited prose files.
3. **Apply your alert level** - Reads your config's `MinAlertLevel` and uses it to decide which findings to fix (see [Severity handling](#severity-handling)).
4. **Match your CI** - Reads the Vale job in your repository's GitHub Actions workflows and reproduces that invocation locally on the changed files. This confirms they pass before creating the suggestion.

Vale only runs on prose content. Code blocks, commands, configuration, frontmatter, schemas, and tables are excluded from linting.

## Severity handling

Vale classifies violations into three severity levels:

| Severity       | Behavior                                                                               |
| -------------- | -------------------------------------------------------------------------------------- |
| **error**      | Blocking. Promptless fixes these before creating the suggestion.                       |
| **warning**    | Advisory. Promptless evaluates against your existing style and fixes when appropriate. |
| **suggestion** | Advisory. Promptless considers these but may preserve intentional style choices.       |

How Promptless treats findings depends on whether your config sets `MinAlertLevel`.

### When MinAlertLevel is set

Setting `MinAlertLevel` is a deliberate choice about the severity bar your docs hold to. Promptless honors it and fixes every finding Vale reports at or above that level, including warnings and suggestions. This mirrors what your Vale CI surfaces, so Promptless resolves the findings you'd otherwise see as review comments before the suggestion reaches you.

For example, with `MinAlertLevel = suggestion`, Promptless fixes every error, warning, and suggestion Vale reports. To have Promptless fix fewer findings, raise the level (for instance, to `warning` or `error`) rather than relying on it to weigh advisory results.

### When MinAlertLevel is unset

When your config doesn't set `MinAlertLevel`, Promptless falls back to treating error-severity rules as hard constraints. Promptless treats warning and suggestion rules as guidance and balances them against the established voice and conventions in your docs.

## CI integration

Vale errors that slip through or arise from later edits are caught by Promptless's automated CI handling. When Vale fails in a GitHub Actions workflow on a Promptless PR, Promptless analyzes the failure and pushes fixes to the branch automatically.

This works alongside other CI checks like broken link detection and Doc Detective tests, giving you layered quality gates without manual triage.

## Create a Vale config

If you don't have a Vale configuration yet, create a `.vale.ini` file in your docs repository root:

```ini
StylesPath = .vale/styles
MinAlertLevel = warning

[*.md]
BasedOnStyles = Vale
```

This minimal config enables Vale's built-in rules. For more comprehensive style enforcement, add external packages:

```ini
StylesPath = .vale/styles
MinAlertLevel = warning

Packages = Microsoft, write-good

[*.md]
BasedOnStyles = Vale, Microsoft, write-good
```

See the [Vale documentation](https://vale.sh/docs/) for detailed configuration options and available style packages.

## Turn your style guidance into rules

Promptless turns your organization's style guidance into one set of style rules that every connected doc collection uses. Before it creates a suggestion in any collection, Promptless checks its draft against the set, even in a repository that doesn't run Vale. Promptless records the set under `style/rules/` in your [Agent Knowledge Base](/docs/for-docs/get-the-most-out/agent-knowledge-base).

Promptless refreshes the set each time it analyzes a doc collection. That happens when you connect a docs repository and each time Promptless re-analyzes one. It also refreshes the set when you give it a style guide or ask it to enforce yours.

Promptless reads style guidance from these sources:

- `style/client_style_guide.md` in your Agent Knowledge Base, and every source it names
- Style guides in your connected docs repositories
- Style guides you give Promptless
- [Agent instruction files and Agent Skills](/docs/for-docs/connect/doc-locations/how-promptless-learns-your-docs) in your docs repositories that govern how your docs are written
- Vale rules a person on your team wrote

When two sources disagree, `style/client_style_guide.md` decides. When it's silent, Promptless writes neither rule and asks you which source holds.

This capability complements Vale enforcement (see [What Promptless does](#what-promptless-does)). Enforcement lints your prose against the Vale rules you already have, and this capability writes the rules themselves from your style guidance.

### Give Promptless your style guide

To have Promptless enforce a style guide, send it to Promptless. Attach the file, link to it, share it from Google Drive, or paste its text in a message. Promptless converts a PDF, DOCX, or HTML guide to Markdown and saves the copy under `style/rules/sources/`, with the guide's origin and version. Later runs and every writer read that copy.

Later runs fetch a linked or Google Drive guide again from its origin, and replace the copy when the guide changed. To update an attached guide, attach the new file.

When Promptless can't fetch or convert a guide in full, it stops and tells you which guide it couldn't read. Promptless writes rules only from complete guides.

### Rules Vale can't check

Some stated rules depend on meaning, such as whether "may" expresses permission or possibility, or whether the items in a list are parallel. No Vale check can express them. Promptless records each one as a judgment rule in `style/rules/judgment-rules.md`, with a one-line restatement, its source, and an example of the rule broken and followed. Promptless applies these rules while it drafts, alongside the Vale rules.

### Keep your rules in a repository

Some teams keep their Vale rules in a repository of their own, such as a style package that every docs repository installs. To make that repository the home of your rules, add it as a doc collection and name it in `style.rules_collection` in your [configuration](/docs/for-docs/reference/configuration-reference#style):

```yaml
style:
  rules_collection: acme/style-guide
```

With a rules collection set:

- Before each run, Promptless syncs its Knowledge Base set from the repository's default branch. Rule files your team wrote stay as written.
- Promptless proposes its rule changes to the repository as one suggestion on the `promptless/style-rules` branch.
- Promptless lints with the Knowledge Base copy, so a change you merge in the repository reaches Promptless at its next sync.

The rules collection must be a GitHub or GitLab repository.

Without a rules collection, the Knowledge Base set is the canonical copy. Promptless proposes the set to a docs repository only when that repository's team asks for it, for example to run the rules in CI.

### Supplement or bootstrap your Vale setup

When your collection already has a Vale configuration, Promptless supplements it with the proposed rules. When your collection has no Vale configuration, Promptless can bootstrap one so the rules have a place to run. A bootstrapped config arrives inside the same suggestion, so nothing lands in your repository without your review.

### How guidance maps to severity

Promptless sets each rule's severity from how firmly your guidance states it:

- A rule your guidance states without exception becomes an error-level rule.
- A rule your guidance hedges, or lists exceptions for, becomes a warning-level rule.
- A convention Promptless observes across your docs becomes an advisory rule at suggestion level. Promptless pools the sampled pages of your connected collections. The convention must hold on at least 8 of them, and on at least 80% of the pages where it appears. When the dominant form differs between collections, Promptless writes no rule.

Rules from stated guidance belong to a `StyleGuide` style, and rules from observed conventions belong to an `Observed` style. Vale prints the style name on every alert, so a reviewer can tell which rules your team wrote down.

For how Promptless acts on each severity once the rules run, see [Severity handling](#severity-handling).

### You decide what gets enforced

Promptless never promotes an observed convention to an enforced rule. To enforce one, write it into `style/client_style_guide.md`. The next run reads it as stated guidance and sets its severity to match.

### Fix existing violations in a collection

When Promptless analyzes a doc collection and your organization already has style rules, it checks the collection's pages against them. It then opens a suggestion that fixes the violations it finds. You can also ask Promptless to fix a collection's style violations at any time.

The suggestion fixes violations of error-level rules only, which are the rules your guidance states without exception. It skips warning-level rules, observed conventions, and Promptless's default style rules. It also skips your repository's own Vale rules, which your CI already reports.

Promptless judges each match before it edits:

- A match that breaks the stated rule gets the smallest edit that satisfies the rule.
- A match on text the rule allows is a false positive. Examples are a word used as a different part of speech, or a match inside code or an exact UI label. Promptless leaves the text unedited, lists it in the suggestion description, and narrows the rule so it stops matching that text.

Each suggestion opens at low priority, on a branch that starts with `promptless/style-violations`, and edits at most 30 files. While it's open, later runs update it. After you merge or close it, the next run opens a new suggestion for the files that remain. The description lists the rules applied with their sources, the violations fixed and remaining for each rule, and each false positive with its reason.
