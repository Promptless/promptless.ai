## Overview

Promptless posts a notification to Slack or Microsoft Teams when a documentation suggestion is ready for review. Customize notifications to:

- Send suggestion notifications to the channels your team watches, per doc collection.
- Send escalations, the messages about configuration and access problems that block Promptless, to a separate channel or email address.
- Change when Promptless notifies and what its messages contain.

<Aside type="tip">
  You can also ask Promptless in Slack or Microsoft Teams to set up notifications for you. For example, "@Promptless send suggestion notifications to my #docs-review channel." See [Ask Promptless to update your configuration](/docs/for-docs/get-the-most-out/ask-promptless-to-update-config).
</Aside>

## Before you start

- An admin role in your Promptless organization, to edit the [Configuration page](https://app.gopromptless.ai/configuration) and the Agent Knowledge Base.
- [Slack](/docs/for-docs/connect/triggers/slack-messages#connect-slack) or [Microsoft Teams](/docs/for-docs/work-the-queue/reviewing-from-slack-and-teams#connect-microsoft-teams), connected to Promptless.

## Choose notification channels

Set the default notification channel in the `policies` section on the [Configuration page](https://app.gopromptless.ai/configuration), and add rules that override it for specific doc collections or triggers:

```yaml
policies:
  default:
    notification:
      slack_channel: docs-updates
      msteams_channel: "19:0a1b2c3d@thread.tacv2"
  
  rules:
    - if:
        doc_collection: acme/internal-docs
      then:
        notification:
          slack_channel: internal-docs-team
```

Slack channel names don't need the `#` prefix. When a Slack channel is renamed, Promptless updates your configuration automatically. `slack_channel` and `msteams_channel` are independent, so a policy can notify Slack, Teams, both, or neither.

<Aside type="note">
  You can route notifications to any Slack channel by name, including one created after you connected Slack. Promptless resolves the channel when you save the configuration that routes to it. Mentioning `@Promptless` in a channel also adds that channel to the dashboard channel pickers. For a private channel, invite Promptless first by running `/invite @Promptless` in the channel.
</Aside>

### Disable an inherited channel

A rule can turn off a channel that it would otherwise inherit from `policies.default` or an earlier rule by setting the field to `null`:

```yaml
policies:
  default:
    notification:
      slack_channel: docs-updates

  rules:
    - if:
        doc_collection: acme/internal-docs
      then:
        notification:
          slack_channel: null
```

Here, suggestions for `acme/internal-docs` send no Slack notification, while every other collection still notifies `docs-updates`. Setting `slack_channel: null` disables the inherited channel, and omitting the field inherits it. `msteams_channel` works the same way, and you disable each channel independently.

### Notify a Microsoft Teams channel

To announce suggestions in a Teams channel, set `msteams_channel` in a policy. Teams channels are addressed by their conversation ID, a value that looks like `19:…@thread.tacv2`. Copy it from Teams. It's the same ID you use for an `msteams_listen` trigger.

<Aside type="note">
  The Promptless bot needs prior activity in a Teams channel before it can deliver notifications there. If Promptless can't reach the configured channel, it replies in the originating thread instead.
</Aside>

See the [Configuration Reference](/docs/for-docs/reference/configuration-reference#policies) for the complete policies schema.

## Escalation channel

Escalation channels receive problem reports, which describe configuration and operational problems that someone on your team needs to fix. Promptless sends two kinds:

- A trigger problem is one Promptless hits while working on a trigger. For example, a PR references a Jira issue Promptless can't read because the Jira integration isn't connected. Or the test account lacks the feature flags to reach a screen Promptless needs to screenshot.
- A connection alert comes from the daily [connection check](/docs/for-docs/reference/integrations#proactive-notifications), such as an integration that needs reconnecting.

Route problem reports to a dedicated channel on Slack, Teams, or both, with an `escalation` section next to `notification`. It takes the same channel fields, plus `email`:

```yaml
policies:
  default:
    notification:
      slack_channel: docs-updates
      msteams_channel: "19:0a1b2c3d@thread.tacv2"
    escalation:
      slack_channel: docs-escalations
      msteams_channel: "19:4e5f6a7b@thread.tacv2"
      email:
        - docs-team@example.com
```

Problem reports reach these channels even when suggestion notifications are off or no notification channel is set. `slack_channel` routes them to Slack; `msteams_channel` routes them to Teams.

If `escalation` leaves out a platform's channel, trigger problems go to your `notification` channel on that platform instead. Connection alerts never do. The next section spells out the rules.

### When problem reports go to the notification channel

Promptless picks the destination for Slack and for Teams separately. On each platform, a problem report goes to the `notification` channel only when all three of these are true:

1. It's a trigger problem. Connection alerts never go to a `notification` channel.
2. `escalation` leaves out that platform's field: `slack_channel` for Slack, `msteams_channel` for Teams. If the field names a channel, the report goes there. If the field is `null`, the report goes nowhere on that platform.
3. A `notification` channel is set for that platform for the trigger.

Promptless resolves both sections for a trigger problem from `policies.default` plus the rules that match the trigger. Connection alerts use only the `escalation` channels in `policies.default`; rules don't change where they go.

When someone asks Promptless for the work by tagging it in a Slack or Teams thread, Promptless reports a trigger problem in that thread instead.

For example, this policy sets an escalation channel for Slack and leaves Teams out:

```yaml
policies:
  default:
    notification:
      slack_channel: docs-updates
      msteams_channel: "19:0a1b2c3d@thread.tacv2"
    escalation:
      slack_channel: docs-escalations
```

| Problem report                                       | Slack              | Teams                                             |
| ---------------------------------------------------- | ------------------ | ------------------------------------------------- |
| A PR references a Jira issue Promptless can't read   | `docs-escalations` | `19:0a1b2c3d@thread.tacv2` (notification channel) |
| The connection check finds GitHub needs reconnecting | `docs-escalations` | Nothing                                           |

To keep the Jira problem out of Teams, add `msteams_channel: null` under `escalation`.

<Aside type="caution">
  If you set only a `notification` channel, connection alerts reach no channel. A broken integration then shows up only on the [Integrations page](https://app.gopromptless.ai/integrations).

  To receive these alerts, set at least one of `slack_channel`, `msteams_channel`, or `email` under `escalation` in `policies.default`.
</Aside>

To also escalate by email, list one or more addresses under `escalation.email`. Promptless emails only the addresses you list, and only for escalations. Suggestion notifications don't use email, and `notification` has no email setting, so Promptless emails escalations only when you set `escalation.email`. Email escalation requires email delivery for your deployment. It's on by default for Promptless-hosted deployments, and self-hosted deployments must configure it.

Trigger problems include blockers such as these:

- A test or staging account that can't reach a needed screen
- An unreachable or unconfigured integration
- An expired or rejected credential
- A missing permission
- A configuration mismatch

Every escalation opens with a bold banner line that names its kind:

- `Blocked — one thing needed from you`: A blocker names the resource, quotes what Promptless saw, and notes any workaround it applied. It ends with a `Need:` line naming the one action that clears the blocker and a `Next:` line saying what happens once you answer.
- `Heads up — worth a look`: A pointer names something Promptless noticed that you can act on. For example, a published page might link to an anchor that no longer exists. It ends with one `Suggested:` action.

## Notification preferences file

Promptless reads the `doc_workflow/notification_preferences.md` file in your [Agent Knowledge Base](/docs/for-docs/get-the-most-out/agent-knowledge-base) whenever it writes a notification. Write your preferences there in plain language. Anything you leave out keeps Promptless's default behavior.

To edit the file, open **Settings** in the Promptless dashboard, select **Agent Knowledge Base**, and open `doc_workflow/notification_preferences.md`.

### What you can customize

The preferences file overrides these defaults:

- **When to notify.** Which events send notifications, and when to skip them.
- **Delivery.** Where a notification goes, such as a reply in the originating Slack thread or a comment on the GitHub pull request.
- **Message format.** The fields, order, and links your suggestion notifications carry. A format you state replaces the default format completely.

### Example customizations

Teams commonly add instructions like these:

**Change notification timing:**

```
Only send notifications for suggestions that modify more than one file.
Skip notifications for automated triggers that don't yield documentation updates.
```

**Adjust delivery preferences:**

```
Always reply in the originating Slack thread when the trigger came from Slack.
Use GitHub comments when reviewers are already engaged with the source PR.
```

**Customize message style:**

```
Use a casual, friendly tone in all notification messages.
Include enough context that someone new to the thread can understand why Promptless is posting.
```

An instruction that only sets tone, like this one, keeps the default fields and links and changes how the message reads.

**Define a message format:**

```
Format suggestion notifications as:
What changed: <one-line summary>
Promptless suggestion: <dashboard link>
MR: <docs PR/MR link>
Assigned: <assignee>
cc: <mentions>
```

A full format like this one replaces the default message format. Promptless posts exactly the fields and links you list, in the order you list them, and adds nothing else. The example lists no Knowledge Base link, so its notifications carry none. A stated format applies to suggestion notifications only. Escalations keep their own format, and a blocker always ends with what Promptless needs from you and what happens next. A mention rule you state applies to every message Promptless sends.

When no format is stated, Promptless sends one or two sentences on what changed and why, followed by labeled link lines:

```
<what changed and why it changed>

Triggered by: <link to the pull request, merge request, or ticket that started the work>
Review: <dashboard suggestion URL>
Docs PR: <docs pull request or merge request URL>
Recorded: <Knowledge Base file URL>
Open question: <a decision only you can make>
```

`Recorded:` repeats once for each Knowledge Base file the work changed. `Open question:` appears at most once, and only when a decision rests with you alone. Promptless leaves out any line that has no value for a given notification. A requested mention still appears where one applies. This default format applies when the preferences file is absent or still holds only its placeholder text. If the file exists but can't be read, Promptless holds the notification and sends nothing in the default format.

A message can name a ticket, issue, or merge-request key, such as `INC-879`. When Promptless knows that key's target, it renders the key as a link. The ticket that started the work is one such target. Any other key stays plain text. This linking adds no field, so it also applies when you've stated your own format.

## Slack notification features

In Slack, Promptless posts each suggestion notification as a preview card. Select the card to open the suggestion in Promptless, or use its buttons to publish the suggestion or open its PR without leaving Slack. A thread reply attaches the full diff of the documentation changes.

### Suggestion preview cards

Each preview card shows:

- **Title**: The suggestion title
- **Status badge**: Shows "New suggestion" for first notifications or "Updated suggestion" for follow-ups
- **Description**: A short excerpt of the suggestion description
- **Triggered by**: A descriptive label linking to the source that triggered the suggestion. Examples include "Merged GitHub PR #123 in acme/docs" or "Slack direct @mention"
- **Files**: The number of files changed
- **Status**: The current suggestion lifecycle status (Open, Pull Request, Published, or Rejected)

<Aside type="tip">
  When your documentation repository has a protected branch, Slack notifications show **Create PR** or **View PR** in place of **Publish**.
</Aside>

### Direct messages to MCP submitters

Someone can submit a documentation task through an [MCP editor](/docs/for-docs/connect/triggers/mcp), such as Claude Code or Cursor. Promptless then sends that person a Slack direct message when the suggestion is ready for review. The suggestion then isn't also posted to the channel. Direct messages to submitters are available in Slack only.

If Promptless can't reach the submitter by direct message, it posts to the configured notification channel. That happens when Slack isn't connected, the `users:read.email` permission is missing, or no Slack account matches the submitter's email.

<Aside type="note">
  Direct messages require the [Slack integration](/docs/for-docs/reference/integrations/slack) to be connected with the `users:read.email` permission. The submitter's Slack account email must also match their Promptless account email. That is the address shown as "Authorize as \{email}" at MCP authorization.
</Aside>

## Post status updates in Slack threads

Promptless can post a follow-up in a suggestion's original Slack thread when the suggestion resolves. The people who asked for the update then see how it ended. To turn this on:

<Steps>
  1. In the [Promptless dashboard](https://app.gopromptless.ai/), open **Settings** and select **Organization**.

  2. Under **Suggestion Status Updates**, check **Post Slack follow-ups when suggestions are resolved**.

  3. Select **Save**.
</Steps>

Promptless then posts one reply in each relevant Slack thread when:

- The docs PR merges.
- The docs PR closes without merging.
- Someone closes the suggestion in the dashboard.
- Promptless archives the suggestion after a period of inactivity.

Delivery is best-effort. The suggestion's status changes even if the Slack post fails.
