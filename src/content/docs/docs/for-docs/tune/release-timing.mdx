## Overview

A documentation suggestion is most useful when it arrives as the change becomes real for your users. Drafted too early, it documents work your reviewers haven't finished. Drafted too late, the docs trail the release. Align two things with your release cycle:

- **When Promptless drafts.** The trigger event decides this. It can be a pull request opening or merging, a commit landing, a feature flag changing, or a call from your pipeline.
- **When a suggestion publishes.** The publishing policy decides whether a suggestion waits for review or merges on its own.

Both use the trigger and policy settings you already have on the [Configuration page](https://app.gopromptless.ai/configuration).

<Aside type="tip">
  You can also ask Promptless in Slack or Microsoft Teams to adjust timing for you. For example, "@Promptless switch my acme/api PR trigger to run on first approval." See [Ask Promptless to update your configuration](/docs/for-docs/get-the-most-out/ask-promptless-to-update-config).
</Aside>

## Match the trigger event to your release stage

<Steps>
  1. On the **Triggers** tab of the [Configuration page](https://app.gopromptless.ai/configuration), expand your **GitHub pull requests** trigger.

  2. Under **When should Promptless run?**, select one or more moments in a pull request's life:

     | Option                       | Activates when                         | Choose it when                                                                          |
     | ---------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------- |
     | **When it's opened**         | A pull request opens                   | You want documentation drafted alongside the code, so reviewers evaluate both together. |
     | **When it's first approved** | A pull request gets its first approval | You want Promptless to analyze the change after a reviewer has vetted it.               |
     | **When it's merged**         | A pull request merges                  | You want documentation only for changes that have made it into the code base.           |

  3. Select **Save changes**.
</Steps>

A new GitHub pull request trigger starts with **When it's opened** and **When it's merged** selected. If suggestions keep arriving before a change has settled, move to a later stage. Select both an early and a late option when you want early feedback and a refresh after merge. See [Choose trigger modes](/docs/for-docs/connect/triggers/github-prs#choose-trigger-modes) for the full behavior of each mode, and the [Configuration Reference](/docs/for-docs/reference/configuration-reference#triggers) for the underlying `trigger_on` field.

<Aside type="note">
  **When it's first approved** activates once per pull request, on the first approval only. Later approvals, and re-approvals after requested changes, don't start another run. If you merge your own pull requests without a separate reviewer, it never activates. Use **When it's merged** or a commit trigger instead.
</Aside>

To keep suggestions current while a source pull request changes, add `updated` to the trigger's `trigger_on` list in YAML. This mode is available only in YAML. Promptless then re-reviews the open pull request each time someone pushes new commits to it. It runs far more often than the options in the table. Scope it to specific repositories and `trigger_directories`. See [Re-review open PRs on every push](/docs/for-docs/connect/triggers/github-prs#re-review-open-prs-on-every-push).

## Document only what has shipped

To document changes once they land, add a [commit trigger](/docs/for-docs/connect/triggers/github-commits), which activates when commits reach a monitored branch.

<Steps>
  1. On the **Triggers** tab, add a GitHub commit trigger.
  2. Point it at the branch you want to watch.
  3. Save your changes.
</Steps>

Pair the commit trigger with your PR trigger to get both timings. Promptless comments on pull requests while they're open, then refreshes the suggestion with the final content once the change merges to your default branch.

A commit trigger on its own, without a PR trigger, is the quietest option. Promptless runs only after changes reach the monitored branch.

## Control when a suggestion publishes

Trigger timing decides when Promptless drafts. Publishing policies decide when a suggestion publishes. By default, a suggestion waits for someone to review and publish it. The defaults on the **Policies** tab of the [Configuration page](https://app.gopromptless.ai/configuration) apply to every suggestion. A rule overrides them for a specific trigger or doc collection.

Some changes can publish without review, such as internal documentation or changelog updates you want live as soon as the change lands. For those, add a rule scoped to a trigger you trust:

<Steps>
  1. On the **Policies** tab, add a rule.
  2. Under **When this matches**, set **Trigger** to the trigger you trust.
  3. Under **Promptless does this**, turn on **Open a pull request automatically**.
  4. Turn on **Merge the pull request automatically**.
  5. Save your changes.
</Steps>

With both on, Promptless merges each docs PR from that trigger as soon as it creates it. Auto-merge requires automatic PR creation. Suggestions from every other trigger still wait for review. For every policy field and its default, see the [Configuration Reference](/docs/for-docs/reference/configuration-reference#policies).

<Aside type="note">
  Publishing policies resolve at publish time, not when the trigger activates. If you change a policy while Promptless drafts a suggestion, the new values apply when that suggestion publishes.
</Aside>

## Documentation PRs open as drafts until the source PR merges

A docs PR (a merge request on GitLab) opens as a draft when it links to a source pull request that is still open. When that source pull request or merge request merges, Promptless marks the docs PR ready for review. When a docs PR links to more than one source pull request, Promptless waits for all of them to merge or close. A docs PR that links only to merged or closed source pull requests opens ready for review. This works the same way on GitHub, GitHub Enterprise, and GitLab.

A suggestion with no linked source pull request opens ready for review immediately. That includes suggestions from Slack, Jira, MCP, or the API.

## Trigger from a feature-flag rollout

When a feature ships behind a flag, its pull request can merge weeks before users see the change. Pull request and commit timing then drafts the docs long before they're relevant. A [LaunchDarkly flag trigger](/docs/for-docs/connect/triggers/launchdarkly) starts documentation work when the flag changes, which is when flagged features reach users.

The trigger requires the [LaunchDarkly integration](/docs/for-docs/reference/integrations/launchdarkly), which is in beta. To connect it, follow [Connect LaunchDarkly](/docs/for-docs/connect/triggers/launchdarkly#connect-launchdarkly).

## Trigger from a deploy or release pipeline

If your release happens in a CI/CD pipeline, use the [API trigger](/docs/for-docs/connect/triggers/api) to request documentation work over HTTP. Add a step after the release completes that calls Promptless and passes release context. The docs then update on the same event that ships the product:

```bash
curl -X POST "https://api.gopromptless.ai/triggers" \
  -H "Authorization: Bearer sk-pl-your-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "instructions": "Document the rate limiting feature released in v2.5.",
    "context": { "release": "v2.5.0" }
  }'
```

The `context` object is optional metadata that appears in the trigger's history. See [API triggers](/docs/for-docs/connect/triggers/api) for the full request format.

<Aside type="tip">
  These inputs combine. Most teams start by matching the PR trigger event to their review stage. They then add a flag or pipeline trigger for features whose release moment isn't the merge.
</Aside>
