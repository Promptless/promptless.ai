**Used for: Triggers, Context, and Publishing**

Promptless connects to GitLab in two directions. Promptless uses a GitLab **access token** — a group access token or a personal access token with the `api` scope — to pull information from GitLab: merge requests, repository files, and project metadata. GitLab uses **webhooks** to notify Promptless when merge requests change. A single group connection covers all three jobs: triggers, context, and publishing. Promptless supports both gitlab.com and self-hosted GitLab.

## Installation

Setup has two parts: create an access token in GitLab, then connect it in Promptless.

<Steps>
  1. **Create a GitLab access token with the `api` scope.** This can be a group access token or a personal access token. Creating a *group* token requires the group Owner role. To create a group access token, go to your group's **Settings > Access Tokens** in GitLab and click **Add new token**. To create a personal access token, open your avatar menu and go to **Edit profile > Access > Personal access tokens**. Either way:

     - Name it (for example, "Promptless").
     - Set an expiration date (maximum one year).
     - Select the **`api`** scope.

     Create the token and copy it immediately. GitLab shows it only once. For more details, see [GitLab's access token documentation](https://docs.gitlab.com/security/tokens/).

  2. **Open the [Integrations](https://app.gopromptless.ai/integrations) page** in the Promptless dashboard.

  3. **Start the GitLab connection.** For a gitlab.com group, find the **Connect GitLab** tile and click **Connect**. For a self-hosted instance, use the **Connect self-hosted GitLab** tile and enter your **Instance hostname** — the hostname only, without a scheme or path.

  4. **Fill in the connection details.** Enter the group's full path in the **Group path** field, paste your token into the **Access token** field, and click **Connect**.
</Steps>

<Aside type="caution" title="Required to connect">
  Connecting needs an access token with the **`api`** scope, plus the target group's path. Promptless verifies the scope inline at connect time, before fetching any project. The **Maintainer** role governs per-project webhook eligibility; see [Token scope considerations](#token-scope-considerations) for how a token's role shapes which projects get automatic webhooks.
</Aside>

<Aside type="note" title="Connect multiple GitLab groups">
  Each GitLab connection covers one group and its subgroups, so to cover more than one top-level group you connect one token per group. Connecting a second group keeps the first — every group you connect stays active. You can connect any combination: sibling or nested (subgroup) groups, and groups on different GitLab instances (gitlab.com and self-hosted). To add another group, click **Connect GitLab** (or **Connect self-hosted GitLab**) again on the Integrations page and repeat the installation steps with that group's token.
</Aside>

## Connected groups

Each connected group appears as its own card on the [Integrations](https://app.gopromptless.ai/integrations) page. Each card is titled `GitLab (gitlab.com)` for a gitlab.com connection, or `GitLab · <host>` for a self-hosted instance. Every card shows a `Host:` line (`gitlab.com` for a gitlab.com connection, or the self-hosted domain) and a `Group:` line with the connected group. The card lists the connected group's projects by full path (for example, `promptless-engineers/<repo>`), sorted alphabetically.

The card also reports project counts by state: how many projects are visible, webhook-eligible, active, ineligible, and failed. Each state means:

- **Visible** — the token can see the project.
- **Webhook-eligible** — the token has Maintainer access on the project, so a webhook can be installed.
- **Active** — a webhook is installed and confirmed.
- **Ineligible** — the token sits below Maintainer, so Promptless doesn't install a webhook automatically.
- **Failed** — Promptless attempted to install a webhook and it didn't succeed. Retry with the **Automatic webhooks** control, or check the token's role on that project.

When a token has Maintainer access on only some of its visible projects, the card reads like "8 of 12 project webhooks active" and lists the rest as ineligible because they sit below Maintainer.

The card's manual **Refresh** re-syncs the project inventory. Projects added to a group after you connect it appear only after you refresh.

## Project setup

After connecting your GitLab account, you can configure how Promptless interacts with your projects:

### Repository access

When setting up a project with GitLab as a trigger source:

1. Select the GitLab projects you want Promptless to monitor for changes. You choose from the projects that have a confirmed webhook; see [Project selection](/docs/for-docs/connect/triggers/gitlab-merge-requests#project-selection) for how the picker is populated.
2. Optionally, configure directory-specific triggers to focus on particular parts of your codebase.

### Directory-specific triggers

You can configure Promptless to only trigger documentation updates when changes are made to specific directories in your GitLab projects. This is useful for:

- Focusing on code that directly impacts user-facing features
- Monitoring API changes that require documentation updates
- Ignoring internal tooling or test changes that don't affect documentation

To set up directory-specific triggers:

1. In your project configuration, select the GitLab project.
2. Under **Advanced Options**, enable **Directory-Specific Triggers**.
3. Enter the directories you want to monitor, separated by commas (for example, `src/api, docs/reference`).

## Merge request link resolution

When you share a GitLab.com merge request link in a Slack message or other trigger, Promptless automatically fetches the MR content. This includes:

- MR metadata (title, state, source/target branches, author)
- Discussion comments with file positions and resolved state
- The full diff for analysis

This allows Promptless to gather context from linked merge requests.

<Aside type="note">
  Merge request link resolution currently works only for gitlab.com. Self-hosted GitLab instances are supported for webhook-based triggers but not for link resolution.
</Aside>

## Source code reading

Promptless can read source files directly from your GitLab projects when processing merge requests or researching documentation updates. This provides context from implementation details that aren't visible in merge request diffs alone.

Promptless uses the GitLab CLI (`glab`) to fetch file contents from your repositories. This is useful when:

- A merge request references code in files that weren't changed
- A new feature needs to be understood in the context of existing code
- Documentation requires accurate details about implementation behavior

<Aside type="note">
  Source code reading works with gitlab.com projects. Self-hosted GitLab instances support webhook-based triggers but not source code reading.
</Aside>

## Publishing documentation to GitLab

Beyond triggers and context, a GitLab project can also be a doc collection—a place where your documentation lives and where Promptless publishes updates. When documentation needs to change, Promptless clones the project, edits files on a new branch, pushes that branch, and opens a merge request for you to review, the same way it opens pull requests on GitHub.

To publish to GitLab, your connected access token needs the write-capable `api` scope—the same scope the integration already uses for triggers. Promptless writes only to the projects you set up as doc collections.

GitLab doc collections work on both gitlab.com and self-hosted GitLab, and both are set up the same way. The project picker lists your connected GitLab projects across every connected instance, and a **GitLab host** field on the same form takes your self-hosted hostname — leave it blank for gitlab.com. See [GitLab projects](/docs/for-docs/connect/doc-locations/gitlab-projects) for setup details and [the configuration reference](/docs/for-docs/reference/configuration-reference#doc-collections) for the `platform: gitlab` and `host` fields.

Promptless tracks merge request status the same way it tracks GitHub pull request status. Because GitLab has no draft flag at creation time, Promptless marks a draft merge request with a `Draft:` title prefix.

Auto-merge differs from the GitHub path—on GitLab, Promptless attempts the merge immediately instead of waiting for a pipeline—so see [Automatic merge request creation](/docs/for-docs/connect/doc-locations/gitlab-projects#automatic-merge-request-creation) before you enable it.

## Authentication model

The GitLab integration authenticates with a GitLab access token:

- **Access token**: A group access token or a personal access token with the `api` scope.
- **Webhook Triggers**: Work with both gitlab.com and self-hosted GitLab instances; automatic webhook setup runs per project, on the projects where the token has Maintainer access.
- **Publishing (doc collections)**: Works with both gitlab.com and self-hosted GitLab instances.
- **Link Resolution**: Works with gitlab.com only.
- **Source Code Reading**: Works with gitlab.com only.

The token's scope and role limit what Promptless can do; see [Token scope considerations](#token-scope-considerations) for which projects it can reach and how Promptless enforces the per-project boundary.

### Token scope considerations

The only hard requirement to connect is the **`api`** scope. The `api` scope is write-capable, so a token that has it can push branches, open merge requests, and read project content — everything Promptless needs to deliver a documentation change. Promptless checks for the scope inline when you connect, before it fetches or saves any project, so you can correct the token on the spot.

A low group-level role still connects, because a token's direct project memberships can grant stronger access than its group role. Promptless evaluates access per project.

A group access token is a GitLab bot identity, so Promptless applies its bot avatar to the merge requests and comments it creates. A personal access token represents its human owner, and that owner's own `@promptless` merge-request comments can invoke Promptless. For a team or org-wide rollout, a group access token is org-owned and keeps working across staffing changes, while a personal access token stays tied to its owner's continued access.

The **Maintainer** role is a per-project webhook-eligibility condition. Promptless reads the full tree of visible projects along with a Maintainer-level inventory, then installs merge-request webhooks on the webhook-eligible projects — including the projects the token reaches through direct project membership. Projects below Maintainer stay visible for context and publishing, and you add a webhook for them by hand in GitLab. Adding a webhook by hand also requires the Maintainer role on that project, so if you don't have it, ask a project Maintainer or Owner. To install webhooks across the eligible projects at once, use the **Automatic webhooks** control on the connection's card.

Promptless writes only to the projects you configure as doc collections. That is an application-level restriction Promptless enforces.

Two layers limit what Promptless can reach. The first is a hard, token-level limit: if you scope a group access token to a group or subgroup that contains only your documentation projects, the token can't reach anything outside it. This is safe only when your trigger and context source projects and your docs-destination projects all live within that same group or subgroup. Otherwise the token can't reach the source projects outside it. A personal access token isn't scoped to a subgroup this way: its reach is the projects its owner can access, so keep it least-privilege by limiting the owner's memberships or using a dedicated account, or use a group access token scoped to a docs-only subgroup. The second layer is an application-level path scope on the doc collection, which limits which files Promptless can change.

## Webhook management

Promptless installs webhooks on the GitLab projects where the token has Maintainer access, to monitor merge request events. These webhooks:

- Trigger Promptless when merge requests are created or updated
- Send only the necessary information about changes to Promptless
- Can be customized to focus on specific events

The **Automatic webhooks** control on the connection's card reinstalls webhooks across the projects where the token has Maintainer access. See [Token scope considerations](#token-scope-considerations) for how webhook eligibility is determined per project.

## Usage

Once configured, the GitLab integration works similarly to other code hosting integrations:

1. When a merge request is opened or updated in your monitored projects, Promptless is automatically triggered.
2. Promptless analyzes the changes to determine if documentation updates are needed.
3. If updates are needed, Promptless generates the appropriate documentation changes.
4. Promptless adds a comment to your GitLab merge request with a link to review the documentation changes.
5. You can review and approve the suggested documentation updates in the Promptless dashboard.

For more information on how triggers work in general, see the [Triggers](/docs/for-docs/connect/triggers) documentation.
