**Used for: Triggers, Context, and Publishing**

Promptless connects to GitLab in two directions. Promptless uses a GitLab **group access token** to pull merge requests, repository files, and project metadata from GitLab. GitLab uses **webhooks** to notify Promptless when merge requests change. Because the token belongs to a group, one group connection covers triggers, context, and publishing for that group's projects. Promptless supports both gitlab.com and self-hosted GitLab.

## Installation

Create a group access token in GitLab, then connect it in Promptless.

<Steps>
  1. **Create a GitLab group access token.** You need the **Owner** role for the group, since GitLab restricts group access token creation to group Owners. If you don't have it, ask a group Owner to create the token. In GitLab, go to your group's **Settings > Access Tokens** and select **Add new token**, then:

     - Name it (for example, "Promptless").
     - Set an expiration date (maximum one year).
     - Select the **`api`** scope.
     - Choose the **Maintainer** role.

     Select **Create group access token** and copy the token immediately. GitLab shows it only once. The token starts with `glpat-`. For more details, see [GitLab's group access token documentation](https://docs.gitlab.com/user/group/settings/group_access_tokens/).

  2. **Open the [Integrations](https://app.gopromptless.ai/integrations) page** in the Promptless dashboard.

  3. **Start the GitLab connection.** For a gitlab.com group, find the **GitLab** tile and select **Connect GitLab**. For a self-hosted instance, use the **Self-hosted GitLab** tile, select **Connect Self-hosted GitLab**, and enter your **Instance hostname**. Enter only the host, with no `https://` and no path (for example, `gitlab.acme.com`).

  4. **Enter the group path and paste the token.** In the **Group path** field, enter the group's full path (for example, `acme/platform`). Paste the token into the **Access token** field, then select **Connect**.

     <img src="https://promptless-customer-doc-assets.s3.us-east-2.amazonaws.com/docs-images/org_3DaVKUzHgjyjaODgCPaDmjXezqp/gitlab-connect-modal-aeb67dd0.png" alt="Connect GitLab modal with Group path and Access token fields and a Connect button" />
</Steps>

<Aside type="caution" title="Required scope">
  The token must be a group access token with the **`api`** scope and the **Maintainer** role. GitLab has no read-only token that works with Promptless, and creating webhooks requires the Maintainer role. See [Token scope considerations](#token-scope-considerations) for why.
</Aside>

<Aside type="note" title="Connect multiple GitLab groups">
  A GitLab group access token grants access to one group and its subgroups. To cover more than one top-level group, connect one token per group. Connecting a second group doesn't replace the first, and every group you connect stays active. You can connect any combination: sibling or nested (subgroup) groups, and groups on different GitLab instances (gitlab.com and self-hosted). To add another group, select **Connect GitLab** or **Connect Self-hosted GitLab** again on the Integrations page. Then repeat the installation steps with that group's token.
</Aside>

### Refresh a group's project list

Each connected group has its own card on the [Integrations](https://app.gopromptless.ai/integrations) page, listing the group's projects by full path (for example, `promptless-engineers/<repo>`). Promptless reads the project list when you connect the group. To pick up projects added to the group later, select **Refresh access** on the group's card.

## What Promptless does with GitLab

A connected group gives Promptless these capabilities:

| Capability                    | What Promptless does                                                                                 | gitlab.com | Self-hosted GitLab |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- | ---------- | ------------------ |
| Merge request triggers        | Reviews merge requests that open or merge in monitored projects, and suggests documentation changes. | Yes        | Yes                |
| Merge request link resolution | Fetches a merge request's content when you share its link in a Slack message or other trigger.       | Yes        | No                 |
| Source code reading           | Reads files from your projects for context that a merge request diff doesn't show.                   | Yes        | No                 |
| Publishing                    | Opens merge requests with documentation updates in projects you set up as doc collections.           | Yes        | Yes                |

### Merge request triggers

When a merge request opens or merges in a project you monitor, Promptless runs automatically:

1. Promptless analyzes the changes to determine whether documentation needs updates.
2. If it does, Promptless generates the documentation changes.
3. Promptless comments on the merge request with a link to review the documentation changes.
4. You review and approve the suggested updates in the Promptless dashboard.

To choose which projects Promptless monitors, add a [GitLab merge request trigger](/docs/for-docs/connect/triggers/gitlab-merge-requests) and select its projects. To trigger only on changes in specific directories, such as `src/api` or `docs/reference`, fill in **Only when files in these folders change** on the trigger (`trigger_directories` in YAML). Use it to focus on user-facing code and API changes, and to skip internal tooling and test changes. For how triggers work in general, see [Triggers](/docs/for-docs/connect/triggers).

### Merge request link resolution

When you share a gitlab.com merge request link in a Slack message or other trigger, Promptless fetches the merge request's content. That content includes:

- The title, state, source and target branches, and author.
- Discussion comments, with file positions and resolved state.
- The full diff.

<Aside type="note">
  Merge request link resolution works only for gitlab.com. Self-hosted GitLab instances support webhook-based triggers but not link resolution.
</Aside>

### Source code reading

Promptless reads source files directly from your GitLab projects when it processes merge requests or researches documentation updates. It fetches file contents with the GitLab CLI (`glab`). Source code reading helps when:

- A merge request references code in files that it doesn't change.
- A new feature makes sense only in the context of existing code.
- Documentation needs accurate details about implementation behavior.

<Aside type="note">
  Source code reading works with gitlab.com projects. Self-hosted GitLab instances support webhook-based triggers but not source code reading.
</Aside>

### Publishing documentation to GitLab

A GitLab project can also be a doc collection: a place where your documentation lives and where Promptless publishes updates. When documentation needs to change, Promptless clones the project, edits files on a new branch, and pushes that branch. It then opens a merge request for you to review, the same way it opens pull requests on GitHub.

Publishing uses the write-capable `api` scope that the connected group access token already has for triggers. Promptless writes only to the projects you set up as doc collections.

GitLab doc collections work on both gitlab.com and self-hosted GitLab, and you set them up the same way. The project picker lists your connected GitLab projects across every connected instance. For a self-hosted project, enter its hostname in the **GitLab host** field. Leave the field blank for gitlab.com. For setup details, see [GitLab projects](/docs/for-docs/connect/doc-locations/gitlab-projects). For the `platform: gitlab` and `host` fields, see [the configuration reference](/docs/for-docs/reference/configuration-reference#doc-collections).

Promptless tracks merge request status the same way it tracks GitHub pull request status. GitLab has no draft flag at creation time, so Promptless marks a draft merge request with a `Draft:` title prefix.

With auto-merge on, Promptless attempts the merge immediately. If GitLab can't merge it yet, for example because a required pipeline hasn't passed, the merge request stays open for you to merge. See [Automatic merge request creation](/docs/for-docs/connect/doc-locations/gitlab-projects#automatic-merge-request-creation) before you enable it.

## Authentication model

The GitLab integration authenticates with a group access token that meets these requirements:

| Requirement | Value              | Why                                                                                   |
| ----------- | ------------------ | ------------------------------------------------------------------------------------- |
| Token type  | Group access token | One token covers a group and its subgroups. GitLab lets only group Owners create one. |
| Scope       | `api`              | Connecting a group creates webhooks, which a read-only `read_api` token can't do.     |
| Role        | Maintainer         | Creating the merge-request webhooks requires the Maintainer role.                     |

The token's scope and role limit what Promptless can do. See [Token scope considerations](#token-scope-considerations) for which projects it can reach and why Promptless, not the token, enforces the per-project boundary.

### Token scope considerations

GitLab has no read-only option. Connecting a GitLab group always writes to GitLab with the group access token. Promptless creates the merge-request webhooks across the group's projects, and it also sets the Promptless bot avatar. Webhook creation is the hard blocker. A read-only `read_api` token can't create those webhooks, so the group connects but delivers no merge request triggers. Promptless offers a [GitHub (read-only) app](/docs/for-docs/reference/integrations/github-read-only), but GitLab has no equivalent. Even a setup that uses GitLab only for triggers and context needs a write-capable token.

Maintainer is the effective requirement for any GitLab connection, whether you use it as a trigger and context source, a docs destination, or both. Publishing on its own (pushing a branch and opening a merge request) needs at least the Developer role. Every connection also sets up the merge-request webhooks, and creating them requires Maintainer. A Developer-role token completes the initial connection, but Promptless can't create its webhooks and doesn't report the failure. The connection then fails on the next refresh, so a Developer-role token isn't a viable option. Use the `api` scope with the Maintainer role.

Two layers limit what Promptless can reach:

- The token's group is a hard, token-level limit. A token scoped to a group or subgroup that contains only your documentation projects can't reach anything outside it. That setup works only when your trigger and context source projects live in the same group or subgroup as your documentation projects. Otherwise the token can't reach the source projects.
- The doc collection is an application-level limit. Promptless enforces it, and the token doesn't. Promptless writes only to the projects you configure as doc collections, and a doc collection's path scope limits which files Promptless can change.

## Webhook management

Promptless sets up webhooks in your GitLab projects automatically to monitor merge request activity. Each webhook subscribes to these GitLab events:

| GitLab event         | What Promptless does with it                                                                                                                                                                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Merge request events | Starts a review when a merge request opens or merges.                                                                                                                                                                                                                        |
| Comments             | Picks up merge request comments that mention Promptless, so a tagged comment can request documentation work. See [Request documentation via merge-request comments](/docs/for-docs/connect/triggers/gitlab-merge-requests#request-documentation-via-merge-request-comments). |

If a Promptless webhook is missing either event, Promptless restores it the next time it syncs the group's webhooks.

## Frequently asked questions

These answers cover the most common GitLab connection problems:

| Problem                                                                     | Cause                                                                                                        | Fix                                                                                                                 |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| You connected a GitLab group, but no merge request triggers arrive.         | A read-only `read_api` token can't create the merge-request webhooks, so the group connects but stays inert. | Recreate the token with the `api` scope and the Maintainer role, then reconnect.                                    |
| The token has the `api` scope, but you still get no merge request triggers. | A Developer-role token can't create the merge-request webhooks. Only the Maintainer role can.                | Recreate the token with the Maintainer role, then reconnect.                                                        |
| A project you added to the group doesn't appear under the connected group.  | Promptless reads the project list when you connect a group, so it doesn't show projects added later.         | Select **Refresh access** on the group's card on the [Integrations](https://app.gopromptless.ai/integrations) page. |

For why GitLab has no read-only option and why the token needs the Maintainer role, see [Token scope considerations](#token-scope-considerations).
