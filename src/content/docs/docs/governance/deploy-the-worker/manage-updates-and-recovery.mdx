## Overview

By default, the trace analyzer updates automatically to every stable release. The supervisor installed with your deployment applies release changes, migrations, and its own updates. Use this guide to pause or pin those updates and to run the one-time upgrade handoffs that some releases need. It also covers resolving a blocked or failed update, and recovering or retiring a deployment without losing trace data.

The `PIGDeployment` controls on this page apply to installations the supervisor manages. If you chose a [manually managed Helm installation](/docs/governance/deploy-the-worker/manual-helm), your operations team schedules and applies upgrades.

## What updates automatically

The default release policy follows every stable release, including major versions and schema changes:

```yaml
release:
  channel: stable
  paused: false
  pinnedVersion: ""
```

An update covers the analyzer, the supervisor, required database migrations, and generated Kubernetes application resources, within the permissions granted at installation. Each stable release includes a compatible transition for the installed version, Promptless, and customer data. On the way to the target release, the supervisor runs every required intermediate migration. Following the stable channel never authorizes the supervisor to erase data or modify shared infrastructure.

Your team continues to maintain shared clusters, networking, ingress controllers, the bootstrap release's collector Ingress, externally managed secrets, and backup policies. A new access requirement or a failed preflight blocks the update and names the action to take. After you resolve the blocker, the supervisor resumes the stable-release transition with no separate approval for each release.

## Upgrade an existing installation to 0.3.4

PIG 0.3.4 moves the collector Ingress from `PIGDeployment.spec.endpoint` to the bootstrap chart's [`ingress` values](/docs/governance/deploy-the-worker/configuration-reference#bootstrap-chart-values). It also replaces the supervisor's runtime and removes its Ingress permissions. The analyzer is unchanged from 0.3.3: schema revision 4 and PostgreSQL 15–18. Installations bootstrapped with an earlier chart need a one-time operator handoff.

The supervisor cannot apply this change to the shared custom resource definition (CRD) on its own. An installation following the stable channel reports `Blocked=True` with reason `CRDUpgradeUnsupported` until an operator completes the handoff. The handoff keeps the same Ingress object, so its hostname, certificate, and load balancer address stay in place.

Run the handoff from a checkout of the [`v0.3.4` release](https://github.com/Promptless/pig-deploy/releases/tag/v0.3.4) with an explicit Kubernetes context. Follow its [`UPGRADING.md`](https://github.com/Promptless/pig-deploy/blob/v0.3.4/UPGRADING.md) for the exact commands. In outline:

<Steps>
  1. Back up the CRD, every `PIGDeployment`, the existing Ingress, and the bootstrap Helm values. Record the supervisor's running image digest and release catalog.

  2. Wait for `status.phase: complete` with no maintenance Job running. Suspend GitOps reconciliation of the bootstrap release and `PIGDeployment`, then scale every supervisor that shares the CRD to zero.

  3. Remove the whole `spec.endpoint` block from each `PIGDeployment` manifest. Copy its hostname, class, TLS Secret, and annotations into the bootstrap values as `ingress.hostname`, `ingress.ingressClassName`, `ingress.tlsSecretName`, and `ingress.annotations`, and set `ingress.serviceName` to the existing Ingress name, such as `acme-analyzer`. Set the 0.3.4 supervisor image digest. Render the chart and confirm the Ingress matches the saved object.

  4. Apply the 0.3.4 CRD with server-side apply, then apply the updated `PIGDeployment`. Never delete or recreate the CRD or the `PIGDeployment`.

  5. Generate the ownership patch with the release's `scripts/ingress-handoff.py` and apply it to the existing Ingress. The patch transfers the Ingress from the `PIGDeployment` to Helm without changing its spec.

  6. Run `helm upgrade` for the bootstrap release with the prepared values. Confirm the Ingress UID, hostname, certificate, and load balancer address match the backup. Then confirm HTTPS health and that the deployment returns to `Ready=True`, and resume GitOps reconciliation.
</Steps>

Removing the endpoint settings changes the analyzer's configuration once, so the supervisor revalidates it after the upgrade. Do not delete the Ingress or run `helm upgrade --force`, which can replace it. If the handoff stops before the Helm upgrade succeeds, keep the old supervisor stopped and repair forward from the saved objects. Do not restart the old supervisor against the updated CRD.

## Upgrade a 0.3.4 installation to 0.3.5 or later

The supervisor sets the analyzer's environment variables, so the two must use the same variable names. A 0.3.4 supervisor sets `INSTRUCTION_HUB_*` variables, and the analyzer in 0.3.5 and later reads `PIG_*` variables. The supervisor updates its own image only after it rolls out the new analyzer. A 0.3.4 installation therefore cannot reach 0.3.5 or later on its own. Replace the supervisor first with a one-time bootstrap upgrade. The `PIGDeployment`, Secrets, storage, and Ingress stay in place.

Use the `pig-supervisor` chart for the highest version in the [stable catalog](https://github.com/Promptless/pig-deploy/blob/main/catalog/stable.json). An unpinned supervisor selects that release, so the bootstrap image matches the release it installs. The chart's values are unchanged from 0.3.4, so you can reuse your current bootstrap values with the new supervisor image digest.

<Steps>
  1. Set `PIG_VERSION` to that version. Download and verify its files. See [Select and verify a release](/docs/governance/deploy-the-worker/deploy-the-analyzer-worker#1-select-and-verify-a-release). Save the current `PIGDeployment`, Ingress, supervisor Deployment, and bootstrap Helm values.

  2. Set `spec.release.paused` to `true`. Wait for `status.phase: complete` with no migration Job running.

  3. Scale the supervisor Deployment to zero and wait for its Pod to terminate.

  4. While the supervisor is stopped, apply a `PIGDeployment` with `channel: stable`, `paused: false`, and no `pinnedVersion`.

  5. Upgrade the bootstrap release with the new chart:

     ```bash
     helm upgrade pig-supervisor "./pig-supervisor-${PIG_VERSION}.tgz" \
       --namespace pig-system --values supervisor-values.yaml \
       --wait --timeout 5m
     ```

  6. Confirm that the supervisor completes the transition. Check that `currentVersion` shows the new release and that the deployment reports `Ready=True` without `Blocked=True`.

  7. Confirm that the Ingress UID, hostname, certificate, and load balancer address match the saved objects, then check HTTPS health and collector access.
</Steps>

Pausing release adoption does not stop the 0.3.4 supervisor from reconciling the analyzer, so stop the supervisor before you change the release policy. If the `PIGDeployment` already shows a `targetVersion` of 0.3.5 or later, contact Promptless before you stop the supervisor.

## Keep cloud infrastructure in Terraform

Your platform team owns database sizing, native object storage, IAM, networking, and backup and retention policy. The supervisor uses application data access and scoped Kubernetes permissions. It does not resize databases or mutate cloud infrastructure.

If a release needs a cloud change, PIG reports `Blocked=True` with the unmet requirement and required operator action. Review and apply the change through Terraform, then let PIG rerun its checks. An unpaused deployment resumes its stable-release transition once the live checks and any required release confirmations pass.

PIG checks dependencies through its application connections. It does not read Terraform state or keep a copy of provisioned capacity. Your platform team checks requirements PIG cannot verify directly, such as managed database disk headroom. Use the provider's metrics to confirm that requirement for the target release. Connectivity alone does not prove sufficient capacity.

A blocked target can coexist with a healthy installed version. Avoid broadening the supervisor's permissions to bypass an infrastructure requirement. Keep the [bootstrap ownership handoff](/docs/governance/deploy-the-worker/gitops-ownership) in place while changing customer-owned infrastructure.

## Follow an update

The supervisor records the current release, target release, update stage, and a durable migration history. The update sequence is:

<Steps>
  1. Resolve and verify the stable release artifacts and its supported upgrade path.

  2. Check hosted compatibility, storage access, and model and repository requirements. Check observable capacity and require operator confirmation for release requirements that cannot be verified directly.

  3. Require release-specific recovery confirmation before a destructive migration, then run the release's coordinated schema migrations. Your backup workflow creates and retains the recovery points.

  4. Roll out the analyzer and supervisor in the release's declared order.

  5. Verify health, storage access, and hosted synchronization before marking the target installed.
</Steps>

An update completes while analysis is disabled or no instruction repositories are selected, so you can upgrade an installation without turning analysis on first. [Verifying a complete session](/docs/governance/deploy-the-worker/verify-your-deployment) still requires analysis enabled and at least one selected instruction repository.

Some transitions can keep ingestion running while analysis pauses. A release that needs an ingestion interruption reports that state. Hosts can retry from their retained native ledgers, so do not delete those ledgers during recovery; successful retries depend on the source still being available.

Inspect the status and events with:

```bash
kubectl get pigdeployment acme --namespace pig \
  -o jsonpath='{.status.currentVersion}{" -> "}{.status.targetVersion}{"\n"}'
kubectl describe pigdeployment acme --namespace pig
kubectl logs deployment/pig-supervisor --namespace pig-system --tail=100
```

The `PIGDeployment` reports these conditions:

| Condition       | Meaning                                          | Operator response                                                   |
| --------------- | ------------------------------------------------ | ------------------------------------------------------------------- |
| `Ready=True`    | The current deployment passed supervisor checks. | Continue monitoring real ingestion and analysis.                    |
| `Updating=True` | A release transition is in progress.             | Review the stage and elapsed time; avoid competing manual upgrades. |
| `Blocked=True`  | A required operation cannot proceed.             | Read the reason and resolve the reported dependency or permission.  |

An old deployment can remain ready while its target release is blocked. Use `currentVersion`, `targetVersion`, condition messages, and recent events together. Status never includes secret values or raw trace content.

## Confirm release prerequisites

Keep confirmations in a customer-owned ConfigMap in the deployment's namespace. Reference its name from `spec.release.confirmation.configMapRef`. Your GitOps repository or backup workflow manages this object; the supervisor reads it without cloud-management permissions.

Every confirmation identifies the deployment and exact target release using `deploymentUID` and `releaseDigest`. A confirmation for another deployment or release cannot authorize the transition.

To collect the identifiers for a confirmation:

<Steps>
  1. From a pinned checkout of [pig-deploy](https://github.com/Promptless/pig-deploy), inspect the target release:

     ```bash
     uv run --frozen pig-release-inspect --version REPLACE_WITH_TARGET_VERSION
     ```

     The command validates the catalog and immutable release manifest, then prints `releaseDigest`, `capacityRequirementsDigest`, and the release requirements as JSON.

  2. Copy the digests exactly, including the `sha256:` prefix.

  3. Read `deploymentUID` from the Kubernetes object:

     ```bash
     kubectl get pigdeployment REPLACE_NAME -n REPLACE_NAMESPACE -o jsonpath='{.metadata.uid}'
     ```

  4. Record the capacity or recovery confirmation that the target release requires, as described in the next sections.
</Steps>

The UID binds the confirmation to that Kubernetes object. Recreating the object requires a new confirmation, even if its name and Promptless installation are unchanged.

### Confirm capacity that PIG cannot inspect

When a target release declares operator capacity requirements, review each requirement against current cloud metrics and the capacity needed during migration. Apply any infrastructure change through Terraform first. Record `capacityConfirmedAt`, the target's `capacityRequirementsDigest`, and `capacityEvidence` describing the check.

PIG records this confirmation as an operator acknowledgement and still reruns its live dependency checks. Don't copy Terraform outputs into a capacity ConfigMap, and don't treat a successful Terraform apply as evidence of free space.

### Confirm recovery before a destructive migration

Create and verify coordinated PostgreSQL and object-storage recovery points using your backup workflow. Record their identifiers as `postgresRecoveryPoint` and `objectRecoveryPoint`, with `confirmedAt`, for the exact target release. Check that the recovery points meet that release's freshness requirements and remain available under your retention policy.

The supervisor blocks a destructive migration until this confirmation passes. It checks the confirmation again before migration. Recording an identifier doesn't create a backup or prove that a restore succeeds, so rehearse restoration separately. Capacity acknowledgement and recovery confirmation satisfy different prerequisites, even when they share a ConfigMap.

## Pause release adoption

This pause stops version updates to the worker software. To pause trace analysis, see [Enable and pause trace analysis](/docs/governance/deploy-the-worker/enable-trace-analysis).

In a GitOps deployment, commit this change to `spec.release` in the `PIGDeployment` manifest:

```yaml
release:
  channel: stable
  paused: true
  pinnedVersion: ""
```

For an installation managed directly with `kubectl`, the equivalent command is:

```bash
kubectl patch pigdeployment acme --namespace pig --type merge \
  -p '{"spec":{"release":{"paused":true}}}'
```

A pause stops new release transitions, including supervisor updates. The installed service keeps running, refreshing credentials, and reporting status. A migration that is already running reaches a documented safe checkpoint before the pause takes effect. Don't delete a migration Job to pause it.

A pause applies only to analyzer and supervisor releases. Instruction Hub publishing and host plugin updates follow their own release workflow. Cloud charges continue, and queued traces stay queued.

## Pin a release and return to stable

Set `pinnedVersion` to an exact release identity provided by Promptless. The supervisor verifies the transition before applying it. `paused: true` takes precedence: a pin does not start an update while paused.

```yaml
release:
  channel: stable
  paused: false
  pinnedVersion: "REPLACE_WITH_SUPPORTED_RELEASE"
```

Pinning the installed version holds it while your team investigates an issue. Choosing an earlier release requests a downgrade; it is allowed only when that release supports the current schema and hosted interface. A pin cannot force an incompatible database downgrade.

To resume automatic stable updates, clear the pin and pause in your source manifest. For a directly managed installation:

```bash
kubectl patch pigdeployment acme --namespace pig --type merge \
  -p '{"spec":{"release":{"paused":false,"pinnedVersion":""}}}'
```

Do not patch a GitOps-managed object without updating its source; the GitOps controller can otherwise undo the change. Do not independently pin the supervisor Deployment image: the release policy coordinates supervisor and analyzer versions together.

## Recover from a blocked or failed update

### A dependency or permission check fails

Keep the last healthy version running. Check the reported resource, action, and identity, then repair the underlying condition. Common causes include rotated tokens, unreachable databases, missing object-storage permissions, insufficient capacity, and unavailable model endpoints. If capacity or a cloud permission is required, review and apply the corresponding Terraform change.

The supervisor retries recoverable failures and preserves its progress. Keep the same deployment ID, the `deployment_instance_id` that [`/healthz` returns](/docs/governance/deploy-the-worker/deploy-the-analyzer-worker#6-point-dns-at-the-ingress-and-check-https). Reinstalling under a different ID creates a second identity and leaves the existing deployment unrepaired.

### A migration fails

Record the source and target releases and failed migration identifier. Preserve the database, objects, logs, and migration Job evidence. The supervisor blocks application code that requires the incomplete schema and prevents concurrent migration attempts.

Retry only through the migration's documented resumable path after fixing the cause. If the failure leaves the schema incompatible with the last application release, use a supported forward repair or a coordinated restoration. Rolling back a Deployment or Helm release does not reverse committed PostgreSQL changes.

### The application fails after migration

Use the release's declared rollback compatibility to decide whether the prior application can run against the new schema. The supervisor may revert application resources only when that compatibility is known. Otherwise, hold the deployment and apply a supported forward repair with the Promptless team.

After recovery, repeat the [first-trace verification](/docs/governance/deploy-the-worker/verify-your-deployment), including completed analysis. A healthy controller doesn't prove that the analyzer has recovered.

### The cluster or supervisor is lost

Restore the bootstrap configuration, including its `ingress` values, and original `PIGDeployment` specification into the recovery cluster. Re-establish analyzer workload identity bindings and Secret delivery. Reconnect the same PostgreSQL database and trace objects using the same deployment identity. Restore network paths and certificates before allowing hosts to upload again.

Repeat the bootstrap ownership handoff before creating the restored `PIGDeployment`: for Flux, install the reviewed recovery bootstrap, then suspend its Helm release. The recovered supervisor checks storage access and application compatibility before resuming. Restore or replace cloud infrastructure through Terraform.

If restoring storage from backups, use a coordinated recovery point for PostgreSQL and object storage. Preserve source watermarks and object references together. Do not run two active deployments against the same database during cutover. Confirm the supported recovery release with Promptless before allowing the supervisor to resume migrations.

After an offline restore that leaves canonical trace objects behind the database, requeue them with the [`rebuild-canonical-objects` maintenance command](/docs/governance/deploy-the-worker/manual-helm#inspect-and-repair-worker-storage). Run it while the analyzer is stopped, after the immutable raw and context objects are in place. The analyzer then rewrites each canonical object in the background.

## Monitor ongoing operation

Alert on blocked updates, supervisor reconciliation failures, ingestion failures, growing analysis delay, unavailable model capacity, and backup failures. A normal release transition may temporarily delay analysis; a persistent backlog needs investigation even when `Ready=True`.

Keep the deployment ID, current and target releases, update history, and support contact in your runbook. The [observability guide](/docs/governance/deploy-the-worker/observability) covers the current service's logs and signals.

## Retire a deployment without erasing traces

Removing the `PIGDeployment` cleans up its generated application resources. PostgreSQL, trace objects, external Secrets, backups, and the collector Ingress stay in place.

<Steps>
  1. With Promptless, disable host enrollment and collection for the deployment.

  2. Let accepted work finish, or record what remains queued.

  3. Pause updates.

  4. Remove the `PIGDeployment` through its owning GitOps repository or Kubernetes workflow.

  5. After the supervisor finishes cleanup, uninstall the bootstrap release to remove the supervisor. Uninstalling it also removes the collector Ingress.

  6. Revoke unused application credentials and remove the DNS records.
</Steps>

Delete retained customer data only through your organization's explicit retention and deletion procedure. Uninstalling PIG doesn't grant permission to delete it.
