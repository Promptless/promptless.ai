The worker ships with observability built in. Structured logging runs with no action from you; Datadog APM and Sentry error reporting are opt-in and disabled by default in the chart. This page covers the Helm values and environment that control each one. See [Worker configuration and data](/docs/governance/reference/worker-configuration-and-data) for the full values table.

## Always on

Two things run under the shipped image and chart with no configuration:

- The worker container runs under `ddtrace-run`.
- The worker service process writes structured JSON logging to stdout, and this is always on. Each record carries Datadog-oriented fields: a `timestamp`, `status` (the level), `logger.name`, `message`, any non-standard extras attached to the record, and `error.stack` when exception or stack information is present.

The worker runs analysis in a child process, and the two use different log channels. The service process logs to stdout, as above. The analysis child process writes its logs to stderr, because its stdout is reserved as the machine-readable result channel the parent worker consumes. The child installs the same structured JSON formatter and carries the validated worker log level, so its stderr logs are structured JSON and trace-correlated in Datadog, in the same format as the service.

## Datadog tracing

Datadog APM is opt-in and disabled by default: the image sets `DD_TRACE_ENABLED=false`, and tracing activates only when that value is `true`.

Enable it with Helm by setting `observability.datadog.enabled=true` along with the `env`, `service`, `agentUrl`, and `site` values. That renders `DD_TRACE_ENABLED=true`, unified service tags, `DD_LOGS_INJECTION=true`, and log-discovery pod annotations. It auto-instruments FastAPI and outbound HTTP.

<Aside type="note">
  Datadog APM assumes a Datadog Agent reachable at the `agentUrl` you set. The chart does not ship the Agent itself.
</Aside>

## Sentry error reporting

Sentry is opt-in and disabled by default in the chart. Sentry is initialized only in the worker service and migration processes. When enabled, the service reports uncaught FastAPI and Starlette exceptions and ERROR-level log records as events to a separate Sentry project you provision for the worker; INFO-and-above records become breadcrumbs. Performance tracing is intentionally off, since Datadog owns application performance monitoring, and `send_default_pii` is `False`.

Analysis child processes emit their logs and traces to Datadog, not to Sentry. Sentry events therefore come from the service.

Enable it with Helm by setting `observability.sentry.enabled=true` and pointing `existingSecretName` and `dsnKey` at a Kubernetes secret that holds a DSN for that separate Sentry project. The chart maps that DSN into the process's `SENTRY_DSN`.

<Aside type="caution">
  The chart's `required` guard fails chart rendering only when `observability.sentry.existingSecretName` is empty. It does not verify the secret's contents: if you point it at a secret that is missing or lacks the DSN key, the pod fails to start with a Kubernetes `CreateContainerConfigError` instead. Provision the secret with the DSN key before you enable Sentry.
</Aside>
