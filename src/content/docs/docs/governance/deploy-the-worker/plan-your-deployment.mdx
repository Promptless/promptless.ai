The trace analyzer connects the instructions your team publishes with what happens when agents use them. It receives traces from enrolled hosts, stores them in your infrastructure, and investigates instruction problems using your configured model provider. Technical writers and developers can set up an instruction hub before you deploy trace analysis.

This guide helps your platform team prepare the environment. Use it to agree on ownership, access, and recovery before installing anything.

<Aside type="note" title="Supervisor availability">
  The supervisor is pending implementation. These public guides describe its proposed installation and operating contract; supervisor commands and configuration are not available interfaces today. To deploy the current service, use [Install with Helm](/docs/governance/deploy-the-worker/deploy-the-analyzer-worker).
</Aside>

## Choose an installation path

| Path               | What your team does                                                                             | Availability                           |
| ------------------ | ----------------------------------------------------------------------------------------------- | -------------------------------------- |
| Supervisor         | Install a controller once, declare a PIG deployment, and receive stable releases automatically. | Planned; documented in this guide set. |
| Current Helm chart | Install and upgrade the `instruction-hub-worker` chart, including its database migration hook.  | Available from the Promptless team.    |

The supervisor is intended to manage the trace analyzer, its migrations, and dedicated PIG resources. It will also update itself. You will retain control over release pauses, version pins, credentials, and the infrastructure it is allowed to manage.

## Assemble the deployment

Begin with an existing Kubernetes cluster. The examples use the organization **Acme**, namespace `pig`, and deployment `acme`.

| Dependency                 | Purpose                                                                       | Preparation                                                                                 |
| -------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Kubernetes                 | Runs the supervisor, analyzer, and migration jobs.                            | Reserve a namespace and capacity; use your existing ingress controller.                     |
| PostgreSQL                 | Stores host identity, trace metadata, ingestion progress, and analysis state. | Create a dedicated database and database owner; configure private connectivity and backups. |
| AWS S3                     | Stores raw trace chunks, canonical trace objects, and analysis context.       | Create a private bucket and grant access to the selected prefix.                            |
| Promptless organization    | Registers the deployment, authorizes hosts, and receives findings and status. | Obtain the runtime URL, deployment identity, and install token from Promptless.             |
| Instruction hub repository | Gives the analyzer the instructions to investigate.                           | Supply its canonical GitHub HTTPS URL, numeric repository ID, and `owner/name`.             |
| Model endpoint             | Performs trace analysis.                                                      | Select a supported provider, model, and authentication method; confirm access and quota.    |
| HTTPS endpoint             | Receives policy requests, host check-ins, and trace uploads.                  | Reserve a hostname and certificate reachable from enrolled devices.                         |

All three cloud recipes use S3. An AKS or GKE installation therefore has an AWS dependency for trace storage. If you require Azure Blob Storage or Google Cloud Storage, contact [help@gopromptless.ai](mailto\:help@gopromptless.ai) before provisioning storage.

### Select repository and model access

The current analyzer verifies a GitHub repository and analyzes its `main` branch. Obtain the immutable repository ID rather than deriving identity from its name. A public repository does not need a read token; a private repository needs a token that can verify and read it. GitLab publishing for the instruction hub does not currently imply GitLab support for the analyzer's repository binding.

The analyzer supports `openai`, `azure_openai`, and `aws_bedrock` model providers. OpenAI and Azure use API keys. Bedrock can use an API key or AWS Signature Version 4 with ambient AWS credentials. Select an endpoint and model that support the Responses API. The cloud running Kubernetes does not determine the model provider: for example, a GKE installation can use OpenAI. See the [configuration reference](/docs/governance/deploy-the-worker/configuration-reference) for current settings.

Set an analysis activation timestamp when you are ready to begin. Analysis normally considers traces at or after this time. All analysis settings must be supplied together; storage and successful uploads alone do not enable analysis.

## Establish network paths

| Connection                           | Required path                                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| Enrolled devices → analyzer          | HTTPS on the deployment hostname. Private access is suitable when every device can reach it, such as through a VPN. |
| Analyzer → PostgreSQL                | TCP 5432 over your private network, with database TLS.                                                              |
| Analyzer → S3                        | HTTPS to the bucket's regional AWS endpoint.                                                                        |
| Analyzer → hosted Promptless         | HTTPS for policy, credential checks, findings, and status.                                                          |
| Analyzer → GitHub and model provider | HTTPS for repository verification/download and analysis requests.                                                   |
| Cluster → release artifacts          | Access to the registries and release endpoints supplied with the installation materials.                            |
| Supervisor → cloud management        | Token exchange and HTTPS to each provider's management APIs, when cloud operations are delegated. |

Allow DNS and certificate validation through your network policy. Configure the ingress controller to accept trace uploads without changing their authorization headers or request body. Every ingress, load balancer, and proxy must accept at least 10 MiB for the collector's maximum encoded upload request. The proposed installation example sets this through `endpoint.ingressAnnotations`; adjust the controller-specific annotation when necessary. An interactive login proxy in front of the API must not intercept requests from enrolled hosts.

A private endpoint keeps inbound traffic off the public internet; it does not remove the analyzer's outbound dependencies. See [Trust and data model](/docs/governance/start-here/trust-and-data-model) for what crosses each boundary, including analysis input sent to the model provider.

## Assign ownership before enabling updates

The planned supervisor follows every stable release by default, including releases that change application behavior, schemas, or dedicated PIG infrastructure. This is broader than patch-only updates. An update must still pass compatibility, permission, and data-preservation checks.

| Owner                  | Responsibilities                                                                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Your platform team     | Shared cluster, VPC/VNet, ingress controller, DNS, secret delivery, resource budgets, database and object-storage backup policies.                                     |
| Your GitOps repository | The supervisor bootstrap configuration, `PIGDeployment` specification, and references to externally managed secrets.                                                   |
| Supervisor             | Generated analyzer resources, coordinated migrations, stable release selection, dedicated PIG resource changes within its declared scope, status, and its own updates. |
| Instruction authors    | Hub content, published plugins, and review of proposed instruction improvements.                                                                                       |

Use one owner for each resource. GitOps should reconcile the `PIGDeployment` specification and externally supplied configuration. The supervisor maintains its bootstrap resources, custom resource definition, generated analyzer resources, and migration Jobs within its installed permissions. Follow the [Flux bootstrap handoff](/docs/governance/deploy-the-worker/install-the-supervisor#hand-off-bootstrap-ownership): install the supervisor, suspend its bootstrap `HelmRelease` in Git, verify the suspension, and only then create the `PIGDeployment`. Keep that Helm release suspended while the supervisor manages releases.

The proposed bootstrap uses customer-owned ConfigMap `pig-system/acme-infrastructure`. Its `inventory.yaml` maps `pig/acme` to exact dedicated cloud resource IDs, allowed operations and fields, and separate management identities. The chart references that inventory and the external `pig-supervisor` ServiceAccount. The supervisor cannot edit its own inventory or grants. See the [management boundary](/docs/governance/deploy-the-worker/install-the-supervisor#declare-the-management-boundary) and each cloud recipe for complete examples.

The default empty inventory permits Kubernetes updates and schema migrations, with no cloud management grants. Cloud examples delegate a database sizing field and S3 configuration inspection. Azure and Google Cloud use a native management identity plus separate AWS management credentials for S3. These identities are distinct from the analyzer's database and object-access credentials.

Initial cloud provisioning remains in your infrastructure workflow. Apply the supplied, reviewed permission policy to each management identity. Remove competing Terraform or GitOps reconciliation for fields delegated to the supervisor; keep ownership of all other fields. Creation, deletion, backup and retention changes, IAM grants, and shared resources are outside the proposed default authority.

If a release needs a permission you have not granted, it stops with a reason and required action. It must not grant itself broader authority or skip a required migration. See [Manage updates and recovery](/docs/governance/deploy-the-worker/manage-updates-and-recovery).

## Prepare recovery and capacity

Keep PostgreSQL backups and S3 retention aligned: restoring metadata without its referenced objects can leave traces unreadable. Record the bucket, prefix, deployment identity, credentials, and database backup location in your recovery procedure. Enable storage deletion protection through your cloud's controls.

Start the analyzer with one replica, matching the current chart. Reserve enough CPU and memory for analysis child processes and enough temporary storage for repository checkouts and trace workspaces. Measure ingestion volume, queue delay, database growth, and model usage before increasing capacity; no universal production sizing is assumed by these guides.

The supervisor contract retains the database and trace objects when a deployment is removed. Removing a Kubernetes resource is not a request to erase customer data. Perform any later storage deletion through a separate, reviewed infrastructure change.

## Choose your cloud recipe

- [Deploy on AWS](/docs/governance/deploy-the-worker/deploy-on-aws): EKS, RDS PostgreSQL, S3, and an IAM role for the analyzer.
- [Deploy on Azure](/docs/governance/deploy-the-worker/deploy-on-azure): AKS, Azure Database for PostgreSQL, and S3 with separate AWS authentication.
- [Deploy on Google Cloud](/docs/governance/deploy-the-worker/deploy-on-gcp): GKE, Cloud SQL for PostgreSQL, and S3 with separate AWS authentication.

Each recipe feeds into the same [supervisor installation](/docs/governance/deploy-the-worker/install-the-supervisor) and verifies a first trace through completed analysis.
