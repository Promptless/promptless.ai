PIG uses PostgreSQL for trace metadata, ingestion progress, analysis runs, and synchronization state. Give each deployment a dedicated database and retain it across application upgrades.

## Database requirements

- Use a PostgreSQL version supported by your selected PIG release.
- Grant the application database role ownership of the PIG schema and permission to run its migrations. Do not grant it cloud administrator permissions.
- Allow the analyzer and migration Jobs to reach the database, normally on TCP 5432, over private networking.
- Require TLS and validate the database certificate with the provider's CA bundle and a supported verification mode.
- Configure automated backups, recovery retention, availability, and deletion protection through your infrastructure workflow.

The cloud guides use Amazon RDS for PostgreSQL, Azure Database for PostgreSQL Flexible Server, and Google Cloud SQL for PostgreSQL.

<Aside type="caution">
  Database authentication is separate from a trace bucket's workload identity. Configure it explicitly.
</Aside>

## Deliver the connection string and CA certificate

<Steps>
  1. **Deliver the DSN through your secret manager.**

     Provide `pig-credentials/postgres-dsn` in namespace `pig`, and URL-encode reserved characters in the username and password. Set the TLS mode for the actual certificate configuration. For a database with a hostname-verifiable certificate:

     ```text
     postgresql://pig_analyzer:REPLACE_PASSWORD@REPLACE_DATABASE_HOST:5432/pig?sslmode=verify-full&sslrootcert=/etc/pig/postgres-ca/ca.pem
     ```

     Cloud SQL CA modes and server certificates differ, so follow the [Cloud SQL certificate guidance](https://cloud.google.com/sql/docs/postgres/authorize-ssl) for your instance.

     <Aside type="caution">
       Keep TLS enabled, and resolve a certificate error at its source.
     </Aside>

  2. **Create the CA ConfigMap.**

     Create ConfigMap `pig-postgres-ca` with key `ca.pem` from your provider's CA bundle.

  3. **Reference the DSN and CA in `PIGDeployment`.**

     ```yaml
     storage:
       postgres:
         dsnSecretRef:
           name: pig-credentials
           key: postgres-dsn
         caConfigMapRef:
           name: pig-postgres-ca
           key: ca.pem
     ```

     The CA mounts at `/etc/pig/postgres-ca/ca.pem` in both analyzer and migration containers. Omit `caConfigMapRef` only when the container's trust store already validates the certificate and the DSN does not reference this file.
</Steps>

## Migrations and connection capacity

- PIG coordinates schema migrations with application releases, so keep migration access available during upgrades.
- Reserve database connections for migrations and operations, plus your analyzer replicas.
- Terraform owns the database instance's version, size, networking, and backups. PIG owns its application schema, including its tables and schema migrations. Leave those to PIG so Terraform does not run competing migrations.

## Back up and restore

- Set your recovery objectives before choosing backup retention.
- Record a recovery point that preserves database object references and their corresponding trace objects.
- Configure object lifecycle rules to retain the data your database backups need.
- Before a destructive migration, provide [recovery confirmation for the exact target release](/docs/governance/deploy-the-worker/manage-updates-and-recovery#confirm-recovery-before-a-destructive-migration).
- Your backup workflow owns cloud backups and supplies the recovery-point identifiers.
- Rehearse restoration with an isolated database and trace location. Keep exactly one active deployment against the database during recovery. Do not run a second deployment against it until recovery finishes.
- Follow [updates and recovery](/docs/governance/deploy-the-worker/manage-updates-and-recovery) before restoring production or changing application versions.
