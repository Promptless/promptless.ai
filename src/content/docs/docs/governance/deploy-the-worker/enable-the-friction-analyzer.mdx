Analysis is opt-in. Once the worker is ingesting, you turn on the Friction Analyzer by setting a group of environment variables together, all prefixed `INSTRUCTION_HUB_ANALYSIS_`. This is the configuration decision that turns collected evidence into findings.

## The analysis variable group

Set these together — the analyzer needs the model connection and the repository target to run. For their default values, see the analysis environment-variable table in [Worker configuration and data](/docs/governance/reference/worker-configuration-and-data):

| Variable                                        | Purpose                                                                          |
| ----------------------------------------------- | -------------------------------------------------------------------------------- |
| `INSTRUCTION_HUB_ANALYSIS_ACTIVATION_AT`        | When analysis becomes active.                                                    |
| `INSTRUCTION_HUB_ANALYSIS_MODEL_PROVIDER`       | The model provider: `openai`, `azure_openai`, or `aws_bedrock`.                  |
| `INSTRUCTION_HUB_ANALYSIS_MODEL_AUTHENTICATION` | How the analyzer authenticates to the provider.                                  |
| `INSTRUCTION_HUB_ANALYSIS_MODEL_BASE_URL`       | The provider's base URL.                                                         |
| `INSTRUCTION_HUB_ANALYSIS_MODEL_NAME`           | The model to use.                                                                |
| `INSTRUCTION_HUB_ANALYSIS_MODEL_API_KEY`        | The provider API key. Secret.                                                    |
| `INSTRUCTION_HUB_ANALYSIS_REPOSITORY_URL`       | The hub repository URL the analyzer reads and cites.                             |
| `INSTRUCTION_HUB_ANALYSIS_REPOSITORY_ID`        | The hub repository identifier.                                                   |
| `INSTRUCTION_HUB_ANALYSIS_REPOSITORY_FULL_NAME` | The hub repository full name.                                                    |
| `INSTRUCTION_HUB_ANALYSIS_REPOSITORY_TOKEN`     | The repository token the analyzer uses. Secret.                                  |
| `INSTRUCTION_HUB_ANALYSIS_QUIET_WINDOW_HOURS`   | How long a session must go without new activity before analysis runs.            |
| `INSTRUCTION_HUB_ANALYSIS_MIRROR_ROOT`          | The local root for the repository mirror.                                        |

<Aside type="caution">
  `INSTRUCTION_HUB_ANALYSIS_MODEL_API_KEY` and `INSTRUCTION_HUB_ANALYSIS_REPOSITORY_TOKEN` are secrets. Supply them from your secret store.
</Aside>

## Where analysis input goes

To produce findings, the analyzer sends trace-derived input — a session digest and trace — to the model provider you configure with these variables. That provider is one you choose and authenticate; the transfer is distinct from the metadata projection the worker sends to hosted Promptless. See [Trust and data model](/docs/governance/start-here/trust-and-data-model).

## What enabling produces

Once analysis is active, the Friction Analyzer reads quiet sessions and produces findings. The worker sends each finding to hosted Promptless, which projects it to a GitHub issue in the hub repository. For how a session becomes findings, see [How analysis works](/docs/governance/findings-and-remediation/how-analysis-works); for the finding object and its GitHub surface, see the [Findings reference](/docs/governance/findings-and-remediation/findings-reference).

## Troubleshoot analysis

If analysis is enabled but no findings appear, start with the analysis child process. The worker runs analysis in a separate child process that writes its logs — including any error the model-provider call raises — to stderr as structured JSON, so they surface in Datadog alongside the rest of the worker's logs. See [Observability](/docs/governance/deploy-the-worker/observability) for where those logs go.

Confirm the model connection first. Check that `INSTRUCTION_HUB_ANALYSIS_MODEL_PROVIDER`, `INSTRUCTION_HUB_ANALYSIS_MODEL_BASE_URL`, and `INSTRUCTION_HUB_ANALYSIS_MODEL_API_KEY` point at a provider the analyzer can reach and authenticate to.

A finding may also be absent because a run is still in flight. A run holds a lease and moves through `queued` and `running`, and a run that a newer generation supersedes ends `cancelled` without writing findings. See [How analysis works](/docs/governance/findings-and-remediation/how-analysis-works) for the run lifecycle.
