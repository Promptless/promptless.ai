The supervisor is designed to install and maintain PIG trace analysis in your cluster. You provide storage, access, and deployment settings once. The supervisor then manages application releases, migrations, and its own updates.

<Aside type="note" title="Supervisor availability">
  The supervisor is pending implementation. The chart, `PIGDeployment` resource, and status fields below define a proposed interface; these commands do not install a shipping product today. For the available deployment path, use [Install with Helm](/docs/governance/deploy-the-worker/deploy-the-analyzer-worker).
</Aside>

## Before you begin

Complete [deployment planning](/docs/governance/deploy-the-worker/plan-your-deployment). Prepare infrastructure with steps 1–3 of the [AWS](/docs/governance/deploy-the-worker/deploy-on-aws), [Azure](/docs/governance/deploy-the-worker/deploy-on-azure), or [Google Cloud](/docs/governance/deploy-the-worker/deploy-on-gcp) recipe. Have Helm and `kubectl` available, with your current context pointing to the intended cluster.

If you are following a cloud recipe, use this page for the common bootstrap and base configuration. Apply only the cloud recipe's combined manifest. You do not need to apply this page's base manifest separately.

The proposed installation materials from Promptless consist of a versioned supervisor chart, release artifact identities, a resource/permission inventory, and deployment registration values. In this guide, `./pig-supervisor` means the unpacked chart supplied by the team. It is not a public registry address.

Use one supervisor installation for the `pig` namespace in this example. Install it in `pig-system`. Cluster administrators perform the bootstrap because it installs the `PIGDeployment` custom resource definition and the controller's scoped RBAC. Routine releases should not require cluster-admin access.

## 1. Prepare secrets and the analyzer identity

Create namespace `pig` and a ServiceAccount named `pig-analyzer`. Reuse either resource if your cloud preparation already created it; run only the missing create commands below. Apply the cloud-specific identity configuration from your recipe to that ServiceAccount.

```bash
kubectl create namespace pig
kubectl create serviceaccount pig-analyzer --namespace pig
```

Use your secret manager to deliver a Kubernetes Secret named `pig-credentials` in `pig`. The examples reference these keys:

| Key                | Value                                                                              |
| ------------------ | ---------------------------------------------------------------------------------- |
| `install-token`    | The deployment's `plih_` token supplied by Promptless.                             |
| `postgres-dsn`     | A PostgreSQL connection string for the dedicated database, including TLS settings. |
| `model-api-key`    | The key for the selected model endpoint; omit for Bedrock Signature Version 4.     |
| `repository-token` | Read access to the private GitHub hub; omit for a public repository.               |

Keep plaintext secrets out of Git and Helm command arguments. To create a Secret from protected local files during a pilot, use:

```bash
kubectl create secret generic pig-credentials --namespace pig \
  --from-file=install-token=/secure/pig/install-token \
  --from-file=postgres-dsn=/secure/pig/postgres-dsn \
  --from-file=model-api-key=/secure/pig/model-api-key \
  --from-file=repository-token=/secure/pig/repository-token
```

The file paths are placeholders for files your team prepares; file contents must not include a trailing newline. Omit the repository argument if the repository is public. For ongoing operation, configure your secret manager to rotate the same keys.

If your database needs a supplied CA bundle, create `pig-postgres-ca` with key `ca.pem` from your provider's certificate bundle. The proposed supervisor mounts it at `/etc/pig/postgres-ca/ca.pem` in both analyzer and migration containers.

```bash
kubectl create configmap pig-postgres-ca --namespace pig \
  --from-file=ca.pem=/secure/pig/postgres-ca.pem
```

Create the TLS Secret `pig-tls` in `pig` using your certificate manager. Its certificate must cover the hostname used below. Keep certificate renewal in your existing certificate-management workflow.

## 2. Bootstrap the supervisor

### Declare the management boundary

The supervisor uses its own ServiceAccount, `pig-system/pig-supervisor`. Its cloud management identities are separate from the analyzer's data-access identities. Keep this account, its identity bindings, and its resource inventory in your platform team's GitOps configuration.

Save this proposed bootstrap configuration as `supervisor-infrastructure.yaml`. The empty inventory authorizes Kubernetes application updates and PostgreSQL schema migrations, but no cloud resource operations. A stable release that requires a cloud change will block until the necessary resource and permission are explicitly delegated.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: pig-system
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: pig-supervisor
  namespace: pig-system
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: acme-infrastructure
  namespace: pig-system
data:
  inventory.yaml: |
    version: 1
    deployments:
      pig/acme:
        identities: {}
        resources: []
```

For cloud management, replace the inner `inventory.yaml` value and add the ServiceAccount bindings from your cloud recipe. Use the exact provisioned resource IDs. The examples delegate database sizing and permit inspection of the S3 bucket; they leave backup, retention, deletion, IAM, and networking changes outside supervisor authority.

The proposed inventory contract is:

| Field                       | Meaning                                                                                                          |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `deployments.pig/acme`      | Authorizes only the `PIGDeployment` named `acme` in namespace `pig`. The deployment cannot select another entry. |
| `identities`                | Named management identities, with an explicit provider, principal, and credential binding.                       |
| `resources[].id` / `type`   | Exact cloud resource ID and provider resource type; wildcards and discovery-based adoption are not allowed.      |
| `resources[].identityRef`   | Identity from this deployment's inventory entry used for this resource.                                          |
| `resources[].operations`    | `inspect` reads required resource configuration; `update` permits changes only to `managedFields`.               |
| `resources[].managedFields` | Explicit provider configuration fields delegated to the supervisor. An empty list permits no field changes.      |

Before enabling `update`, remove competing reconciliation for those fields from your infrastructure workflow. Preserve customer ownership of the remaining fields. Apply the reviewed cloud permission policy supplied with the installation materials to each named principal. The inventory constrains supervisor behavior; it does not create IAM grants or make a broad provider role safe.

Save the following proposed chart values as `supervisor-values.yaml`:

```yaml
watchNamespace: pig
serviceAccount:
  create: false
  name: pig-supervisor
infrastructure:
  inventoryConfigMapRef:
    name: acme-infrastructure
    key: inventory.yaml
  credentialSecretNames: []
```

Both references resolve in `pig-system`. The chart grants read access to this inventory and only the management Secrets named in `credentialSecretNames`. Cloud recipes add their required Secret names and pod labels here. The controller must not modify the inventory, credential bindings, or its own permission grants.

Create the bootstrap resources through GitOps, or for a direct installation:

```bash
kubectl apply -f supervisor-infrastructure.yaml
```

Deliver any cloud management Secrets before installing the chart. Review its rendered permissions against the inventory, then use the proposed bootstrap command:

```bash
helm upgrade --install pig-supervisor ./pig-supervisor \
  --namespace pig-system \
  --create-namespace \
  --values supervisor-values.yaml \
  --wait
```

`watchNamespace` restricts customer deployment reconciliation to `pig`. The controller also needs the permissions declared by the chart to maintain its own resources in `pig-system` and its custom resource definition. It must reject a missing inventory entry and report unavailable management identities or permissions before changing cloud resources.

### Hand off bootstrap ownership

If your cluster already uses Flux, use this sequence instead of running the Helm command above. Flux installs the bootstrap release, then you suspend that release before creating a `PIGDeployment`. GitOps continues to reconcile your deployment specification and secret-delivery resources.

This is part of the proposed supervisor contract. Until a `PIGDeployment` exists in its watched namespace, the supervisor must report health and wait without starting release transitions or updating itself. Creating that resource after the handoff enables its release policy.

Prepare this manifest in a path reconciled by your existing Flux installation. Reconcile `supervisor-infrastructure.yaml` and secret delivery before the Helm release. Use Flux controllers that support `OCIRepository` API `v1` and `HelmRelease` API `v2`. Replace the registry URL and digest with the bootstrap chart identity supplied by Promptless. The illustrative registry below is not a published PIG registry.

```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: OCIRepository
metadata:
  name: pig-supervisor
  namespace: pig-system
spec:
  interval: 1h
  url: oci://registry.example.com/promptless/pig-supervisor
  ref:
    digest: sha256:REPLACE_WITH_SUPPLIED_CHART_DIGEST
  layerSelector:
    mediaType: application/vnd.cncf.helm.chart.content.v1.tar+gzip
    operation: copy
---
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: pig-supervisor
  namespace: pig-system
spec:
  interval: 1h
  timeout: 10m
  releaseName: pig-supervisor
  suspend: false
  chartRef:
    kind: OCIRepository
    name: pig-supervisor
  values:
    watchNamespace: pig
    serviceAccount:
      create: false
      name: pig-supervisor
    infrastructure:
      inventoryConfigMapRef:
        name: acme-infrastructure
        key: inventory.yaml
      credentialSecretNames: []
```

Keep `HelmRelease.spec.values` identical to your prepared `supervisor-values.yaml`, including the cloud recipe's additions. These values select the customer-owned inventory and management identity for both installation paths.

The digest fixes the bootstrap artifact. It does not pin later PIG releases. For a private registry, deliver a registry authentication Secret in `pig-system` and reference it through `OCIRepository.spec.secretRef.name`. See Flux's [OCIRepository reference](https://fluxcd.io/flux/components/source/ocirepositories/#secret-reference) for the required Secret format.

Commit the bootstrap manifest and let Flux install it. Keep the `PIGDeployment` out of the reconciled path until the following handoff is complete. Wait for the initial installation:

```bash
kubectl wait helmrelease/pig-supervisor --namespace pig-system \
  --for=condition=ready --timeout=10m
```

Next, change only the `HelmRelease` object's `spec.suspend` to `true` in Git and let Flux apply that commit. Leave the rest of the bootstrap manifest in place. Verify the live value:

```bash
kubectl get helmrelease pig-supervisor --namespace pig-system \
  -o jsonpath='{.spec.suspend}{"\n"}'
```

The result must be `true` before you create the `PIGDeployment` in step 3. Flux's [suspend control](https://fluxcd.io/flux/components/helm/helmreleases/#suspend) stops Helm release reconciliation. Suspending only the `OCIRepository` would not stop reconciliation of the installed release.

After the handoff, ownership is:

| Owner                          | Resources it maintains                                                                                                                                                                                 |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GitOps and your secret manager | The suspended bootstrap manifest, namespaces, `PIGDeployment.spec`, analyzer and supervisor ServiceAccounts, management inventory and identity bindings, external Secrets, and certificate ConfigMaps. |
| Supervisor                     | The bootstrap chart's declared supervisor resources, including its Deployment image and pod configuration; the PIG custom resource definition; generated analyzer resources and migration Jobs.        |

The supervisor remains limited by its installed permissions and declared resource inventory. It must not widen its own RBAC or adopt unrelated resources. Do not add the chart's rendered resources to a separate Flux Kustomization or Argo CD Application. This handoff does not disable reconciliation for other applications.

Keep the bootstrap `HelmRelease` suspended during normal operation. Do not resume it, remove it from Git, or run manual Helm upgrades while the supervisor owns those resources. Use `PIGDeployment.spec.release` for [pause and pin controls](/docs/governance/deploy-the-worker/manage-updates-and-recovery). Follow the recovery or retirement procedure before transferring ownership again.

For a direct Helm bootstrap, there is no continuously running Helm controller to suspend. Keep the bootstrap values for recovery, then create the `PIGDeployment` in step 3 without adding a competing reconciler.

## 3. Declare your PIG deployment

Save the following proposed resource as `pig-deployment.yaml`. Replace every Acme URL, repository ID, bucket, and registration value with your own. `runtimeURL` and `deploymentID` come from Promptless; the examples do not designate a live Promptless endpoint.

```yaml
apiVersion: governance.promptless.ai/v1alpha1
kind: PIGDeployment
metadata:
  name: acme
  namespace: pig
spec:
  release:
    channel: stable
    paused: false
    pinnedVersion: ""
  serviceAccountName: pig-analyzer
  hosted:
    runtimeURL: https://runtime.example.com
    deploymentID: acme-prod
    installTokenSecretRef:
      name: pig-credentials
      key: install-token
  endpoint:
    hostname: traces.acme.example
    ingressClassName: nginx
    tlsSecretName: pig-tls
    ingressAnnotations:
      nginx.ingress.kubernetes.io/proxy-body-size: "10m"
  storage:
    postgres:
      dsnSecretRef:
        name: pig-credentials
        key: postgres-dsn
      caConfigMapRef:
        name: pig-postgres-ca
        key: ca.pem
    s3:
      region: us-west-2
      bucket: acme-pig-traces
      prefix: acme/traces
  analysis:
    activationAt: "2026-09-14T00:00:00Z"
    quietWindowHours: 0.5
    repository:
      url: https://github.com/acme/acme-instruction-hub.git
      id: 123456789
      fullName: acme/acme-instruction-hub
      tokenSecretRef:
        name: pig-credentials
        key: repository-token
    model:
      provider: openai
      authentication: api_key
      baseURL: https://api.openai.com/v1
      name: REPLACE_MODEL_NAME
      apiKeySecretRef:
        name: pig-credentials
        key: model-api-key
```

The proposed resource uses the current worker's repository and model requirements. It does not add support for new storage or model providers. Set the activation time to your intended collection rollout; use the model your account can access. Remove `tokenSecretRef` for a public hub. Remove `caConfigMapRef` only when the database certificate is already trusted by the container's system trust store.

The supervisor maps `hosted.deploymentID` to the current worker's `deploymentInstanceId` and uses the resource name as the deployment name. It resolves the registered configuration hash from the effective deployment configuration and hosted registration. You do not invent a `configHash` or reuse a host enrollment credential as the install token. The current Helm path still requires the configuration values supplied by Promptless.

`ingressClassName` must name an existing controller. The supervisor creates a standard Ingress backed by the analyzer Service, using the four current API paths: `/healthz`, `/v0/host-enrollment/policy`, `/v0/host-enrollment/check-ins`, and `/v0/traces/batches`.

The proposed supervisor copies `ingressAnnotations` to the generated Ingress metadata. The example raises ingress-nginx's [request-body limit](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/annotations/#custom-max-body-size) to 10 MiB, matching the collector's maximum encoded upload request. For another controller, replace that annotation with its equivalent. Every load balancer and proxy on the upload path must also allow at least 10 MiB; the default ingress-nginx limit is too small.

On Azure or GCP, add the following under `spec.storage.s3` after preparing `pig-s3-credentials` as described in the cloud recipe:

```yaml
credentialsSecretRef:
  name: pig-s3-credentials
```

The proposed supervisor injects `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and, when supplied, `AWS_SESSION_TOKEN` from that Secret into the analyzer. It sets the AWS region from `storage.s3.region`. With no credential Secret, the analyzer uses the ambient AWS SDK credential chain, as in the EKS recipe. The supervisor must reconcile Secret changes into the workload so rotated credentials take effect.

Apply the resource after the custom resource definition is installed:

```bash
kubectl apply -f pig-deployment.yaml
kubectl get pigdeployment acme --namespace pig --watch
```

The supervisor should preflight connections and permissions, initialize or migrate the database, start the analyzer, and publish status. The resource name becomes the generated analyzer Deployment and Service prefix: `acme-analyzer`.

## 4. Check deployment status

The proposed status interface reports the installed and target release and Kubernetes conditions named `Ready`, `Updating`, and `Blocked`:

```bash
kubectl get pigdeployment acme --namespace pig \
  -o jsonpath='{.status.currentVersion}{" -> "}{.status.targetVersion}{"\n"}'
kubectl describe pigdeployment acme --namespace pig
kubectl logs deployment/pig-supervisor --namespace pig-system --tail=100
kubectl logs deployment/acme-analyzer --namespace pig --tail=100
```

`Ready=True` means the supervisor has reconciled the configuration and its deployment checks passed. It is not proof that a user trace has completed analysis. A `Blocked=True` condition must identify the failing dependency or required operator action. Do not paste Secrets or raw traces into a support request; include the deployment ID, release, condition, and relevant redacted error.

Point your hostname at the ingress endpoint and check HTTPS from an enrolled device's network:

```bash
curl --fail https://traces.acme.example/healthz
```

This checks routing and the service's health response. Continue with a real trace to verify storage and analysis.

## 5. Verify the complete workflow

1. Confirm the deployment's endpoint and identity with Promptless, then follow [Enroll your hosts](/docs/governance/get-started/enroll-your-hosts) on one supported test device.
2. Start a new agent session after the activation time. Use an installed Acme hub skill and complete the session normally.
3. Confirm the host checks in and the trace appears in Promptless. Check customer storage for that trace's recorded object references and successful ingestion; the hosted trace row alone does not prove every local dependency works.
4. Wait for analysis to complete. A completed analysis with no finding is a successful result. Investigate queued or failed analysis through logs and the hosted status.
5. If a finding is produced, open its evidence and confirm that the installed instructions and relevant host are attributed correctly. Review any proposed remediation before applying it.

Record the session and deployment identity as your installation acceptance evidence. Use [Observability](/docs/governance/deploy-the-worker/observability) to monitor subsequent traffic.

## Troubleshoot initial installation

| Symptom                                 | Check                                                                                                             |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `PIGDeployment` is unknown              | The planned supervisor is not available yet, or its chart/CRD has not been installed in this cluster.             |
| Database preflight is blocked           | Private routing, DNS, database credentials, CA bundle, and schema-owner permissions.                              |
| S3 access is denied                     | Bucket/prefix policy, IAM trust or credential Secret, and KMS key permissions when using a customer-managed key.  |
| Hosts cannot enroll or upload           | Host-network reachability, TLS, deployment registration, policy, credential validity, and ingress body limits.    |
| Traces arrive but analysis stays paused | Activation time, complete model settings, GitHub numeric ID and canonical URL, access to `main`, and model quota. |

After the first successful analysis, configure [automatic updates and recovery](/docs/governance/deploy-the-worker/manage-updates-and-recovery).
