The analyzer worker is the `instruction-hub-worker` service that runs inside your infrastructure. It accepts session traces from enrolled hosts, stores them in your Postgres database and S3 bucket, and runs the [Friction Analyzer](/docs/governance/start-here/how-it-works).

This guide installs the worker into an existing Kubernetes cluster and verifies every connection it needs. Once the infrastructure prerequisites are ready, the installation should take less than 15 minutes.

## What runs where

| Hosted Promptless                                                              | Your infrastructure                                                            |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Deployment registration, configuration sync, and host credential introspection | The worker Deployment and its Kubernetes credentials                           |
| Trace metadata, findings, and remediation workflow                             | Raw traces and canonical trace objects in your S3 bucket and Postgres database |
| Deployment health and last-heartbeat status                                    | Trace analysis through the model provider and endpoint you configure           |

Hosted Promptless never receives raw trace content. Findings can contain model-authored descriptions of a session. See [Trust and data model](/docs/governance/start-here/trust-and-data-model) for the complete boundary.

## Before you begin

You need:

- A Promptless organization with Agent Instructions enabled and permission to manage deployments.
- An existing Kubernetes cluster running a version supported on the deployment setup page.
- Helm 3 and `kubectl` installed locally, with `kubectl` connected to the target cluster.
- Permission to create a namespace, Deployment, Service, ServiceAccount, Secret, migration Job, and optional ingress resources.
- A Postgres database you control for trace and host metadata.
- An S3 bucket you control for raw traces and canonical trace objects.
- An IAM role or equivalent workload identity that lets the worker read and write objects in that bucket.
- A hostname and TLS certificate that enrolled hosts can reach. The endpoint can be private if all hosts are on the same private network.

The worker and installation machine need the following network paths:

| Source               | Destination                   | Port | Purpose                                                    |
| -------------------- | ----------------------------- | ---- | ---------------------------------------------------------- |
| Enrolled hosts       | Worker hostname               | 443  | Enrollment, check-ins, and trace uploads                   |
| Worker               | Hosted Promptless Runtime     | 443  | Configuration sync, credential introspection, and findings |
| Worker               | Postgres                      | 5432 | Trace and host metadata                                    |
| Worker               | S3                            | 443  | Raw and canonical trace objects                            |
| Worker               | Your model provider           | 443  | Trace analysis, once analysis is enabled                   |
| Installation machine | Promptless chart repository   | 443  | Helm chart download                                        |
| Cluster nodes        | Promptless container registry | 443  | Worker image pull                                          |

The deployment setup page lists the exact Promptless hosts and the supported chart and image versions for your organization.

Confirm the target cluster before continuing:

```bash
kubectl config current-context
```

<Aside type="caution">
  The commands below change the cluster in your current `kubectl` context. Switch contexts first if this is not the cluster where the worker should run.
</Aside>

## Install the worker

<Steps>
  1. **Create the worker deployment in Promptless.**

     In hosted Promptless, open your deployment settings and add a deployment for this environment, choosing the Kubernetes with Helm installation option. Enter a name that identifies the environment, such as `production-us-east-1`.

     The setup page provides:

     - A `plih_` install token, displayed once
     - A generated `promptless-worker-values.yaml` file with the Runtime URL, deployment identifiers, S3 bucket, image, and non-secret configuration
     - The supported Helm chart version
     - Environment-specific network requirements and resource recommendations

     Download the values file and copy the install token to your secret manager. If you lose the token before installing, rotate it from the deployment's setup page.

     <Aside type="note">
       The hosted setup page for creating a deployment is being built. Its exact navigation and control labels may differ from the flow described here.
     </Aside>

  2. **Create the Kubernetes Secret.**

     Create a dedicated namespace, then enter the install token and Postgres connection string when prompted:

     ```bash
     kubectl create namespace instruction-hub \
       --dry-run=client -o yaml | kubectl apply -f -

     printf "Worker install token: "
     read -r -s INSTRUCTION_HUB_INSTALL_TOKEN
     printf "\nPostgres DSN: "
     read -r -s INSTRUCTION_HUB_CUSTOMER_POSTGRES_DSN
     printf "\n"

     kubectl --namespace instruction-hub create secret generic instruction-hub-worker-env \
       --from-literal=install-token="$INSTRUCTION_HUB_INSTALL_TOKEN" \
       --from-literal=customer-postgres-dsn="$INSTRUCTION_HUB_CUSTOMER_POSTGRES_DSN" \
       --dry-run=client -o yaml | kubectl apply -f -

     unset INSTRUCTION_HUB_INSTALL_TOKEN
     unset INSTRUCTION_HUB_CUSTOMER_POSTGRES_DSN
     ```

     The secret remains in your cluster because the worker uses both values at runtime. Do not put either value in `promptless-worker-values.yaml` or commit it to source control.

  3. **Add your infrastructure settings.**

     Create a small `values.yaml` next to the generated file. This file contains only the settings specific to your cluster:

     ```yaml title="values.yaml"
     secrets:
       existingSecretName: instruction-hub-worker-env

     serviceAccount:
       annotations:
         eks.amazonaws.com/role-arn: arn:aws:iam::<account-id>:role/instruction-hub-worker

     gateway:
       enabled: true
       hosts:
         - host: traces.example.com
       tls:
         - hosts:
             - traces.example.com
           secretName: instruction-hub-worker-tls

     resources:
       requests:
         cpu: 500m
         memory: 1Gi
       limits:
         memory: 2Gi
     ```

     Replace the role ARN, hostname, and TLS Secret with values for your environment. If another ingress or gateway already routes traffic to Kubernetes services, leave `gateway.enabled` off and route it to the worker Service on port 8080.

  4. **Get the chart source and version.**

     The deployment setup page supplies the chart source and the pinned chart version to install. The worker image is published to `ghcr.io/promptless/instruction-hub-worker`.

     Confirm that the chart version you install matches the one shown on the deployment setup page.

     <Aside type="note">
       A hosted Promptless Helm repository for a one-line `helm repo add` is being built. Until it ships, use the chart source and pinned version shown on the setup page.
     </Aside>

  5. **Install the worker.**

     Replace `<chart-reference>` and `<chart-version>` with the chart source and version shown in Promptless:

     ```bash
     helm upgrade --install instruction-hub-worker \
       <chart-reference> \
       --namespace instruction-hub \
       --version <chart-version> \
       --values promptless-worker-values.yaml \
       --values values.yaml \
       --atomic \
       --wait \
       --timeout 10m
     ```

     The chart runs its database migration Job before starting the worker. If a migration or readiness check fails, `--atomic` rolls back the release instead of leaving a partial installation.

  6. **Confirm the Deployment is available.**

     ```bash
     kubectl wait --namespace instruction-hub \
       --for=condition=available deployment/instruction-hub-worker \
       --timeout=5m
     ```

     The chart marks its mandatory values as `required`, so `helm upgrade --install` fails to render when one is missing or empty, and the pod fails to start when the referenced Secret or key is absent. There is no fail-closed preflight beyond these checks, so verify the worker's host-facing and hosted connections in the next steps.

     <Aside type="note">
       A chart test hook that verifies the worker's health endpoint, Runtime authentication, Postgres schema, and S3 read/write access in a single `helm test` run is being built. Until it ships, use the checks in the following steps.
     </Aside>

  7. **Test the host-facing endpoint.**

     From a machine on the same network as your agent hosts, check the worker's health endpoint:

     ```bash
     curl --fail --silent --show-error \
       https://traces.example.com/healthz
     ```

     Replace the example hostname with your worker hostname. This check confirms that DNS, TLS, and routing work from the network where hosts run.

  8. **Confirm the deployment in Promptless.**

     Return to your deployment settings in hosted Promptless. The deployment should report an online status with a recent heartbeat.
</Steps>

The worker is ready when its Deployment reports available, its host-facing health endpoint responds, and hosted Promptless reports it online with a recent heartbeat. Next, [enroll a host](/docs/governance/get-started/enroll-a-host) and confirm that its first new session appears.

## Enable trace analysis

Installation proves that trace ingestion and storage work. To run the Friction Analyzer, add the `INSTRUCTION_HUB_ANALYSIS_*` settings for:

- The model provider and endpoint that may receive trace-derived analysis input
- The analysis model and its credentials
- The Instruction Hub repository and repository-scoped token
- The quiet window after which a session is eligible for analysis

Keep API keys and repository tokens in the existing Kubernetes Secret. Put non-sensitive settings in `values.yaml`, then run the same `helm upgrade --install` command. See [Enable the Friction Analyzer](/docs/governance/deploy-the-worker/enable-the-friction-analyzer) for the full variable group, [Configure the worker](/docs/governance/deploy-the-worker/configure-the-worker) for how to apply configuration changes, and [Worker configuration and data](/docs/governance/reference/worker-configuration-and-data) for every setting.

## Manage the deployment with GitOps

For a GitOps-managed cluster:

- Commit the generated `promptless-worker-values.yaml` and your non-sensitive `values.yaml`.
- Pin the chart version rather than tracking the latest release.
- Create `instruction-hub-worker-env` through your existing External Secrets, Sealed Secrets, or equivalent controller.
- Preserve Postgres and S3 independently of the Helm release and back them up using your normal policies.
- Test an upgrade in a staging deployment before applying it to production.

## Troubleshoot installation

### The migration job fails

Review the migration logs and confirm the Postgres DSN, network path, database permissions, and supported Postgres version:

```bash
kubectl logs --namespace instruction-hub \
  --selector app.kubernetes.io/component=migration
```

### The worker cannot register

Check worker logs for Runtime connectivity or token errors:

```bash
kubectl logs --namespace instruction-hub \
  --selector app.kubernetes.io/name=instruction-hub-worker \
  --since=15m
```

If the install token was rotated, update `instruction-hub-worker-env` and restart the Deployment.

### The worker cannot access S3

Confirm that the ServiceAccount has the intended workload identity annotation, the pod assumed that identity, and its policy allows reads and writes to the configured bucket.

### Hosts cannot reach the worker

Run the health check from a host network, then inspect the ingress or gateway address and certificate:

```bash
kubectl get service,ingress --namespace instruction-hub
```

### The pod is ready but Promptless does not report the worker online

Confirm outbound HTTPS access to the Runtime URL in `promptless-worker-values.yaml`, then restart the Deployment and recheck the deployment status in Promptless.

If the deployment still fails, send the worker logs and the output of the checks above to [help@gopromptless.ai](mailto\:help@gopromptless.ai). Do not send Secret manifests, tokens, database connection strings, or model credentials.

## Remove the worker

In hosted Promptless, open the deployment and disable it so it stops accepting new hosts and work. Then uninstall the Helm release:

```bash
helm uninstall instruction-hub-worker --namespace instruction-hub
```

The uninstall removes chart-managed Kubernetes resources. It does not delete your Postgres database, S3 objects, or hosted deployment history. Delete those separately only when your retention policy allows it.
