The analyzer worker is the `instruction-hub-worker` service that runs in your Kubernetes cluster. It accepts encrypted session traces from enrolled hosts, stores the decrypted data in infrastructure you own, and runs the [Friction Analyzer](/docs/governance/start-here/key-concepts).

This guide starts with an existing Kubernetes cluster. Promptless Terraform modules provision the worker's cloud dependencies, then a pinned Helm chart installs the worker. You do not need to create a public endpoint, configure DNS or TLS, or write a Helm values file by hand.

## Give this page to a coding agent

Codex, Claude Code, or another coding agent can prepare the installation in your infrastructure repository. Start a task with this prompt:

```text
Install the Promptless analyzer worker by following this guide:
https://promptless.ai/docs/governance/deploy-the-worker/deploy-the-analyzer-worker

Use the existing Kubernetes cluster and the infrastructure conventions in this
repository. Inspect first. Add only the Promptless Terraform and Helm configuration.
Run validation and show me the Terraform plan before applying anything. Never ask me
to paste a Promptless token or another secret into chat. If this repository uses a
pull-request deployment workflow, open a PR instead of applying the changes locally.
```

Tell the agent which cluster and cloud account, project, or subscription to use. It should discover the remaining non-secret values from the existing environment.

<Aside type="caution">
  Review the agent's resolved cloud identity, Kubernetes context, Terraform plan, and chart version before allowing an apply. A coding agent should never approve its own infrastructure plan.
</Aside>

## What the installation creates

| Location                | Resources                                                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------- |
| Hosted Promptless       | Deployment registration, configuration, health status, trace metadata, findings, and remediation workflow     |
| Your Kubernetes cluster | Worker Deployment, bootstrap Job, ServiceAccount, internal Service, migration Job, and Kubernetes credentials |
| Your cloud account      | Managed Postgres, object storage, a secret for the database connection, and least-privilege workload identity |

The default Terraform modules create dedicated data services with encryption, private networking, automated backups, deletion protection, and public access disabled. You can point the modules at compatible existing services instead.

### Outbound-only trace delivery

The worker does not need an ingress. During bootstrap, it creates a deployment key pair inside your cluster and registers the public key with Promptless. Host runtimes encrypt trace batches to that key and send the ciphertext through the Promptless relay. The worker retrieves and decrypts each batch over an outbound HTTPS connection.

Hosted Promptless can route the encrypted payload but cannot decrypt its contents. Plaintext raw traces and canonical trace objects exist only in your worker, database, object store, and configured model provider. See [Trust and data model](/docs/governance/start-here/trust-and-data-model) for the complete boundary.

Allow these outbound connections:

| Source        | Destination                          | Port | Purpose                                                    |
| ------------- | ------------------------------------ | ---- | ---------------------------------------------------------- |
| Worker        | `control.gopromptless.ai`            | 443  | Bootstrap, configuration, heartbeats, and findings         |
| Worker        | `relay.gopromptless.ai`              | 443  | Retrieve encrypted trace batches and send acknowledgements |
| Host runtimes | `relay.gopromptless.ai`              | 443  | Send end-to-end encrypted trace batches                    |
| Worker        | Your Postgres private endpoint       | 5432 | Store trace metadata and coordination state                |
| Worker        | Your object storage private endpoint | 443  | Store raw and canonical trace objects                      |
| Worker        | Your model provider                  | 443  | Analyze traces after you enable analysis                   |
| Cluster nodes | `ghcr.io`                            | 443  | Pull the worker image and Helm chart                       |

No Promptless-owned service needs an inbound route to your cluster or cloud account.

## Before you begin

You need:

- A Promptless organization with Agent Instructions enabled and permission to create deployments.
- An existing Kubernetes cluster on AWS, GCP, or Azure.
- Permission to create cloud data services and workload identity for that cluster.
- Terraform 1.11 or later, Helm 3, `kubectl`, and your cloud CLI.
- A remote, encrypted Terraform backend if this is a production installation.
- A repository for the Terraform and pinned Helm configuration if your team deploys through pull requests.

The installation machine or CI runner must already be authenticated to the target cloud and Kubernetes cluster. Promptless does not request cloud administrator credentials.

## Install the worker

<Steps>
  1. **Create a deployment in Promptless.**

     In hosted Promptless, open **Settings → Deployments**, select **Add deployment**, and choose **Existing Kubernetes cluster**. Enter a name that identifies the environment, such as `production-us-east-1`.

     Keep the setup page open. It provides:

     - A one-time `plih_` bootstrap token, shown once and valid until the first successful installation
     - The supported Terraform module and Helm chart versions
     - The deployment's live installation checks
     - The exact outbound destinations for your organization

     If the token is lost or exposed, rotate it before continuing. Do not give it to a coding agent in chat or store it in a Terraform variable.

  2. **Confirm the target environment.**

     Run the checks for your cloud, then confirm the Kubernetes context and required permissions.

     <Tabs syncKey="worker-cloud">
       <TabItem label="AWS">
         ```bash
         aws sts get-caller-identity
         aws configure get region
         aws eks describe-cluster --name <cluster-name> \
           --query 'cluster.{name:name,status:status,version:version}'
         ```
       </TabItem>

       <TabItem label="GCP">
         ```bash
         gcloud auth list --filter=status:ACTIVE
         gcloud config get-value project
         gcloud container clusters describe <cluster-name> \
           --location <cluster-location> \
           --format='yaml(name,status,currentMasterVersion)'
         ```
       </TabItem>

       <TabItem label="Azure">
         ```bash
         az account show --query '{name:name,id:id,tenantId:tenantId}'
         az aks show \
           --resource-group <resource-group> \
           --name <cluster-name> \
           --query '{name:name,powerState:powerState.code,version:kubernetesVersion}'
         ```
       </TabItem>
     </Tabs>

     ```bash
     kubectl config current-context
     kubectl cluster-info
     kubectl auth can-i create namespaces
     kubectl auth can-i create deployments --namespace promptless
     ```

     Stop if any command resolves to the wrong account or cluster. The last two checks must print `yes`.

  3. **Add the Promptless infrastructure module.**

     Create an `infrastructure/promptless` directory in your infrastructure repository. Add the example for your cloud as `main.tf`, replacing only the values marked with angle brackets.

     <Tabs syncKey="worker-cloud">
       <TabItem label="AWS">
         ```hcl title="infrastructure/promptless/main.tf"
         terraform {
           required_version = ">= 1.11.0, < 2.0.0"

           required_providers {
             aws = {
               source  = "hashicorp/aws"
               version = "~> 6.0"
             }
           }
         }

         provider "aws" {
           region = "<aws-region>"
         }

         module "promptless_worker" {
           source = "github.com/Promptless/terraform-worker-deployment//modules/aws?ref=v1.0.0"

           deployment_name         = "<deployment-name>"
           kubernetes_cluster_name = "<cluster-name>"
           kubernetes_namespace    = "promptless"
           storage_mode            = "create"
         }

         output "promptless_worker_helm_values" {
           value = module.promptless_worker.helm_values_yaml
         }
         ```
       </TabItem>

       <TabItem label="GCP">
         ```hcl title="infrastructure/promptless/main.tf"
         terraform {
           required_version = ">= 1.11.0, < 2.0.0"

           required_providers {
             google = {
               source  = "hashicorp/google"
               version = "~> 7.0"
             }
           }
         }

         provider "google" {
           project = "<gcp-project-id>"
           region  = "<gcp-region>"
         }

         module "promptless_worker" {
           source = "github.com/Promptless/terraform-worker-deployment//modules/gcp?ref=v1.0.0"

           deployment_name             = "<deployment-name>"
           project_id                  = "<gcp-project-id>"
           kubernetes_cluster_name     = "<cluster-name>"
           kubernetes_cluster_location = "<cluster-location>"
           kubernetes_namespace        = "promptless"
           storage_mode                = "create"
         }

         output "promptless_worker_helm_values" {
           value = module.promptless_worker.helm_values_yaml
         }
         ```
       </TabItem>

       <TabItem label="Azure">
         ```hcl title="infrastructure/promptless/main.tf"
         terraform {
           required_version = ">= 1.11.0, < 2.0.0"

           required_providers {
             azurerm = {
               source  = "hashicorp/azurerm"
               version = "~> 4.0"
             }
           }
         }

         provider "azurerm" {
           subscription_id = "<azure-subscription-id>"
           features {}
         }

         module "promptless_worker" {
           source = "github.com/Promptless/terraform-worker-deployment//modules/azure?ref=v1.0.0"

           deployment_name        = "<deployment-name>"
           resource_group_name     = "<resource-group>"
           kubernetes_cluster_name = "<cluster-name>"
           kubernetes_namespace   = "promptless"
           storage_mode           = "create"
         }

         output "promptless_worker_helm_values" {
           value = module.promptless_worker.helm_values_yaml
         }
         ```
       </TabItem>
     </Tabs>

     `storage_mode = "create"` provisions a dedicated managed Postgres instance and object store, places the database connection in the cloud's native secret manager, and grants the worker access through workload identity. The generated Helm values contain resource identifiers and Secret references, never credentials.

  4. **Review and provision the cloud resources.**

     The direct and pull-request paths use the same Terraform files.

     <Tabs>
       <TabItem label="Apply directly">
         ```bash
         terraform -chdir=infrastructure/promptless fmt
         terraform -chdir=infrastructure/promptless init
         terraform -chdir=infrastructure/promptless validate
         terraform -chdir=infrastructure/promptless plan \
           -out=promptless.tfplan
         ```

         Review the plan before continuing. It should create one managed Postgres instance, one object store, one cloud secret, and one workload identity. It must not create or replace the Kubernetes cluster, VPC, virtual network, or existing workloads.

         ```bash
         terraform -chdir=infrastructure/promptless apply promptless.tfplan
         terraform -chdir=infrastructure/promptless output \
           -raw promptless_worker_helm_values \
           > infrastructure/promptless/promptless-worker-values.yaml
         ```
       </TabItem>

       <TabItem label="Open a pull request">
         Add the Terraform module to the repository's existing infrastructure workflow. The agent should open a PR containing the module, its version pin, and any non-secret environment inputs.

         Configure the deployment job to run these stages in order after approval:

         ```bash
         terraform apply <reviewed-plan>
         terraform output -raw promptless_worker_helm_values \
           > "$RUNNER_TEMP/promptless-worker-values.yaml"
         ```

         Pass the generated values file to the existing Helm or GitOps deployment stage as an ephemeral build artifact. Do not commit generated credentials or a Terraform state file.
       </TabItem>
     </Tabs>

     Inspect `promptless-worker-values.yaml`. It is safe to commit if your workflow requires a checked-in values file: it contains only cloud resource identifiers, workload identity, and non-secret worker settings.

  5. **Supply the bootstrap token outside source control.**

     Create a short-lived Kubernetes Secret from a terminal, not from the coding-agent conversation. Paste the one-time token when prompted:

     ```bash
     kubectl create namespace promptless \
       --dry-run=client -o yaml | kubectl apply -f -

     read -r -s -p "Promptless bootstrap token: " PROMPTLESS_BOOTSTRAP_TOKEN
     printf "\n"

     kubectl --namespace promptless create secret generic promptless-worker-bootstrap \
       --from-literal=token="$PROMPTLESS_BOOTSTRAP_TOKEN" \
       --dry-run=client -o yaml | kubectl apply -f -

     unset PROMPTLESS_BOOTSTRAP_TOKEN
     ```

     For a pull-request deployment, create the same one-time Secret through the CI system's protected secret store immediately before the first Helm install. Remove the CI secret after Promptless shows the worker as Online. Do not add it to a GitOps repository.

  6. **Install the pinned chart.**

     Use the chart version shown on the Promptless setup page. The chart is distributed as an OCI artifact, so there is no Helm repository to add.

     ```bash
     helm upgrade --install promptless-worker \
       oci://ghcr.io/promptless/charts/instruction-hub-worker \
       --namespace promptless \
       --version <chart-version> \
       --values <path-to-promptless-worker-values.yaml> \
       --set-string bootstrap.existingSecret=promptless-worker-bootstrap \
       --atomic \
       --wait \
       --timeout 15m
     ```

     The chart exchanges the bootstrap token for a deployment credential, stores that credential in `promptless-worker-identity`, and invalidates the bootstrap token. It then runs database migrations and starts the worker and outbound relay connector.

  7. **Verify every dependency.**

     Run the chart's test and include its logs if a check fails:

     ```bash
     helm test promptless-worker --namespace promptless --logs
     ```

     A passing test verifies:

     - The worker Deployment is available.
     - The deployment credential authenticates with hosted Promptless.
     - The outbound relay connection is active.
     - The Postgres schema is current.
     - An object can be written, read, and deleted through workload identity.

     Return to the deployment setup page. The same checks should be green and the deployment should show **Online** with a recent heartbeat.

  8. **Remove the one-time Secret.**

     After the deployment is Online, delete the consumed bootstrap Secret:

     ```bash
     kubectl delete secret promptless-worker-bootstrap --namespace promptless
     ```

     Keep `promptless-worker-identity`. The worker uses that chart-managed Secret for subsequent starts and upgrades.
</Steps>

The infrastructure installation is complete when the Terraform apply succeeds, the Helm test passes, and hosted Promptless shows the deployment as **Online**. Next, [enroll a host](/docs/governance/get-started/enroll-your-hosts) and enable trace analysis.

## Use existing data services

The default is deliberately opinionated, but the Terraform modules can reuse compatible Postgres and object storage. Set `storage_mode = "existing"` and provide the cloud resource identifiers through the module's `existing_storage` input.

The module validates engine version, encryption, private connectivity, required bucket or container controls, and workload-identity permissions during `terraform plan`. It returns an actionable error instead of allowing Helm to install against an incompatible data layer. Credentials remain in the cloud's native secret manager.

## Enable trace analysis

Bring the worker Online before adding model and repository access. In hosted Promptless, open the deployment and select **Configure analysis**. Choose the model provider, model, Instruction Hub repository, and quiet window.

Use workload identity for AWS Bedrock or another provider that supports it. Store API keys and repository credentials in your cloud's native secret manager, then give the worker identity access to only those Secret versions. Hosted Promptless syncs non-secret analysis configuration; it never stores or returns the credentials.

See [Configuration reference](/docs/governance/deploy-the-worker/configuration-reference) for the underlying settings.

## Keep the installation in source control

Treat the Terraform module version, Helm chart version, non-secret overrides, and deployment name as the installation's source of truth. Upgrades should produce a reviewed plan or pull request that changes explicit version pins.

The bootstrap token and the generated `promptless-worker-identity` Secret are installation state, not configuration. Never commit either one. Back up Postgres and object storage through your normal cloud policies; do not rely on Kubernetes backups for the worker's durable data.

## Troubleshoot installation

### Terraform cannot connect the data services to the cluster

Confirm that the cluster and data services share private network connectivity and that the cloud identity running Terraform can inspect the cluster network. Re-run `terraform plan`; the module reports the failed network or IAM preflight before it changes infrastructure.

### The bootstrap job fails

```bash
kubectl logs --namespace promptless \
  job/promptless-worker-bootstrap
```

Rotate the bootstrap token in Promptless if it expired, was already consumed, or belongs to another deployment. Recreate `promptless-worker-bootstrap`, then retry the Helm installation.

### The migration job fails

```bash
kubectl logs --namespace promptless \
  --selector app.kubernetes.io/component=migration
```

Check private network connectivity, the database Secret reference, database permissions, and the supported Postgres version.

### The relay check fails

Confirm outbound HTTPS access to `control.gopromptless.ai` and `relay.gopromptless.ai`. No ingress, load balancer, public DNS record, or inbound firewall rule is required.

### The worker is ready but Promptless shows Offline

```bash
kubectl logs --namespace promptless \
  --selector app.kubernetes.io/name=instruction-hub-worker \
  --since=15m
```

Check the deployment credential and control-plane connection, then rerun `helm test`.

If the deployment still fails, send the Terraform error, Helm test output, and worker logs to [help@gopromptless.ai](mailto\:help@gopromptless.ai). Do not send Secret manifests, tokens, database connection strings, or model credentials.

## Remove the worker

In hosted Promptless, open the deployment and select **Disable** so it stops accepting new hosts and work. Then uninstall the Helm release:

```bash
helm uninstall promptless-worker --namespace promptless
```

The uninstall removes chart-managed Kubernetes resources and revokes the deployment credential. It does not delete Postgres or object storage. The Terraform modules block destructive data removal by default; deleting retained data requires an explicit opt-in and creates a final database snapshot first.
