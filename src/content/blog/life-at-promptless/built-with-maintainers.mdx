Every docs PR an agent opens lands in a reviewer's queue. In open source, that reviewer is a maintainer who already has more work than time. For the past year, Promptless has put its drafts in front of those maintainers in public. Their reviews shaped our agent, and they shaped [DoGBench](https://dogbench.ai), the documentation benchmark we released this month.

A merge tells us a draft was good enough. A review comment tells us what good means for that project. That second signal is what we built on.

## The work is in the commit history

Vitess and Helm both run Promptless on their docs. When a code change needs documentation, Promptless opens a docs PR. The project's maintainers review and revise it, then decide whether to merge it.

Vitess maintainers have merged [more than 70 docs PRs](https://github.com/vitessio/website/pulls?q=is%3Apr+is%3Amerged+author%3Aapp%2Fpromptless) that Promptless opened on the Vitess website. Some of them have two authors. In [vitessio/website#2144](https://github.com/vitessio/website/pull/2144), Promptless updated the current v24.0 release on the releases page, and Matt Lord added a commit that updated v23 too. The [merged commit](https://github.com/vitessio/website/commit/c710ec3b7b3e31c588a0077d21f705ffcca3cd63) lists Promptless and Matt as co-authors.

Helm maintainers have merged [29 docs PRs](https://github.com/helm/helm-www/pulls?q=is%3Apr+is%3Amerged+author%3Apromptless-for-oss) from Promptless as of mid-October. Review there is hands-on. On [helm/helm-www#2171](https://github.com/helm/helm-www/pull/2171), which added an "Introduction to Helm" overview page, Paige Calvert requested changes in two rounds. She also asked for each fix to be carried over to the v3 docs. After both rounds, she approved it and Terry Howe merged it.

## How Mautic went from reviewer to co-author

Mautic is where that feedback loop went furthest.

Promptless was drafting docs for Mautic by April 2026, and Mautic's Education Team kept a person in the loop from the start. Ayu Adiati describes the setup in her Mautic blog post, [How Mautic pairs Promptless with human review to catch up on docs](https://mautic.org/blog/keep-docs-up-to-date-automatically). "We started by having Promptless watch code PRs and post suggestions on its dashboard. The Education Team then reviewed each one before turning it into an actual PR."

In May, Mautic was one of three projects in our [Write the Docs Portland Writing Day session](/blog/life-at-promptless/wtd-writing-day), alongside Vitess and Helm. Ayu labeled good first issues for attendees to work on.

The same month, Promptless opened [mautic/user-documentation#723](https://github.com/mautic/user-documentation/pull/723) to document a transactional email feature. Ayu left 50 review comments, many of them about Mautic's style guide. She showed us that admonition bodies need a three-space indent and where Vale on and off directives belong. She asked us to spell out abbreviations on first use, write in active voice, use asterisk list markers, and link to specific subsections with `:ref:`. Promptless worked through the comments in rounds, and she merged the PR in June.

We turned that review into an eval case for our agent, named "Mautic docs must follow style guide on first pass." Its rubric listed the style fixes Ayu had made by hand. A draft passed only if a maintainer wouldn't need to raise any of them.

Ayu's September post describes what came next:

> Once we saw how consistently Promptless followed our style guide and aligned with the intent of the code changes, we felt confident in opting into the fully automated workflow.

Ayu then co-authored DoGBench.

## What maintainers taught the benchmark

DoGBench asks whether an agent can produce user-facing documentation that holds up in expert review. Its first question for each item is whether the docs need to change at all. Then task-specific rubrics grade the patch on accuracy, completeness, reader guidance, placement, style, and repository conventions. Those are the things maintainers raise in review, so we checked the benchmark against maintainers directly.

According to [the paper](https://dogbench.ai/paper), project maintainers reviewed 42 items from repositories including Helm, Doc Detective, Mautic, and PostHog. For each item, a maintainer decided whether the docs needed to change. The benchmark's automatic decision agreed with the maintainers on 41 of the 42. In the one disagreement, the benchmark called for a docs change where the maintainer said none was needed.

For the 23 items that needed a change, maintainers built their own grading criteria. They started by leaving GitHub-style inline review comments on candidate patches without knowing which patch was which. Claude Sonnet 4.6 drafted structured criteria from those comments. Each maintainer then edited, added, or deleted criteria and approved each one. Maintainers never saw DoGBench's generated rubrics, and the rubric generator never saw theirs.

DoGBench's generated rubrics covered 220 of those 242 maintainer-validated criteria, or 90.9%. That count is in Table 10 of the paper's [full PDF](https://dogbench.ai/dogbench-paper.pdf). I use it because it counts every criterion across all 23 items. The paper's main text reports a related measure: a mean priority-weighted recall of 0.892 on the 21 items with completed criterion alignment.

The paper notes that one maintainer rubric took roughly 30 minutes to an hour, even for maintainers familiar with the domain. That's the same kind of review Ayu gave on #723, done item by item and turned into criteria a benchmark can apply.
