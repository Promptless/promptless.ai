GitHub processed 986 million commits in 2025. That is a 25% increase from the year before. The main reason: AI coding tools. Teams using Cursor, Copilot, or Claude Code ship 20–30% more code per sprint than they did before those tools existed.

[Documentation drift](/blog/technical/documentation-drift-detection-problem) is already a persistent problem for developer-facing teams. AI tools made the math worse.

More commits means more documentation drift. That relationship is direct. Every code change is a potential gap between what your docs say and what your product does. When the number of changes goes up by a quarter, the number of potential gaps goes up by a quarter too.

The documentation workflows most teams use were designed for a slower pace. They are not keeping up.

## Why drift scales with commit velocity

Documentation drift happens when a code change ships without a corresponding doc update. The usual causes: renamed parameters, deprecated endpoints, restructured flows, new required fields. Each one is small. Together they compound.

The rate of drift is roughly proportional to how often code changes. If a team ships 50 pull requests per week and 10% of them touch something doc-relevant, that is five potential drift points per week. Double the PRs to 100, and you double the drift surface.

AI coding tools did not change the percentage of changes that affect docs. They changed the denominator. Teams that used to merge 40 PRs per sprint now merge 60 or 80. According to the 2025 GitHub Octoverse, the number of pull requests merged on GitHub grew 23% year over year, reaching 43.2 million per month. That is not a small shift.

The 2025 Postman State of the API report found that 55% of API teams already struggle with inconsistent documentation. Those numbers were collected before AI tools hit mainstream adoption rates. The trend is not improving on its own.

## The PR template problem

The standard fix is to add a "did you update the docs?" field to the PR template. This works when developers know which docs are affected. At lower velocity, that is usually the case: the engineer who wrote the feature also knows which pages describe it.

At higher velocity, that assumption breaks down.

When a developer is moving fast with AI assistance, they are often working across multiple areas in a single sprint. A change that renames three API fields touches the reference docs, the changelog, the migration guide, and possibly a tutorial. The developer writing that change may not have written those pages, may not remember they exist, and may not have time to audit them before merging.

The PR template question becomes a checkbox. People check it to get past the review, not because they verified anything. A 2025 GetDX study found that developers already spend three to ten hours per week searching for answers that should be in documentation. That time comes from somewhere: it comes from trusting docs that turned out to be wrong.

This is a process design failure, not a motivation failure. Asking a developer moving fast to audit documentation coverage is asking them to switch context in a way that conflicts with how AI-assisted work actually gets done.

## What faster code changes do to stale docs

There is a secondary effect worth naming. At higher velocity, the window between "doc is accurate" and "doc is wrong" shrinks. A page that was correct at the last sprint review may be stale by the next one. That matters because many teams audit docs on a quarterly or sprint-by-sprint basis.

If your team ships three times more changes per quarter than it did two years ago, a quarterly audit now misses three times as much as it used to. The audit schedule did not change. The change rate did.

The result is that documentation that was 80% accurate two years ago might be 60% accurate today, even if the team is putting in the same amount of doc maintenance effort. The effort stayed constant; the surface area grew.

A 2025 survey found that 60% of documentation becomes outdated within six months. That figure is probably already conservative for teams with high AI adoption. New hires at companies with stale docs take two to three months longer to reach full productivity, according to the same GetDX research cited above. That cost compounds at each sprint.

## What to do about it

The fix is not more process. Adding another PR checklist or expanding the quarterly audit will not close a gap that is growing faster than manual review can track.

The change that actually moves the needle is shifting from audit-based detection to continuous monitoring. Instead of asking "what drifted since the last review?" the system watches for changes and surfaces them as they happen.

Practically, that means connecting your docs to the signals where product changes are recorded: pull requests, changelogs, deployment pipelines, API specs. When a change lands that is relevant to a documented page, the system flags it. Writers review flags, not code repos.

This does not require replacing writers with automation. Writers are still the ones who assess impact and update the page. The change is in how they find out. Surveillance work (scanning PRs and Slack to discover what changed) is what automation handles. Editorial work (deciding what the doc should say) stays with humans.

Promptless monitors the connections between your product and your docs, so your team finds out about drift from a notification rather than a support ticket. As commit velocity increases from AI-assisted development, that kind of continuous coverage becomes the practical baseline for keeping docs accurate.
