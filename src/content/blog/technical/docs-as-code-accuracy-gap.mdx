Your docs-as-code pipeline is green. Lint passes. Links resolve. Every PR goes through review before it merges. Deployment is automated and runs without error.

Your docs are still inaccurate.

This is the gap the docs-as-code community does not talk about much. The tooling ecosystem has built sophisticated workflows for treating documentation like code: version control, pull requests, CI/CD, automated builds. These are real improvements. But they solve a different problem than the one most documentation teams are actually fighting.

The workflow is healthy. The content is not. Those are not the same thing.

## What docs-as-code actually solves

Docs-as-code delivers three concrete improvements worth keeping.

**Version control.** Documentation history becomes auditable. You can see who changed what, when, and in which PR. Reverting a bad edit takes a single command.

**Contributor access.** Engineers who already use Git can submit documentation changes without learning a proprietary CMS. The friction of writing a doc goes down, at least for technical contributors.

**Automated deployment.** Documentation publishes on merge rather than through a manual upload. The build either works or fails. No partial deploys.

These are genuine wins. The point here is not to abandon the workflow. The point is to be precise about what it fixes and what it does not.

Keeping documentation accurate as the product changes is still the top challenge for 56% of API teams, according to the State of Documentation 2026 report. That number has not moved despite broad adoption of docs-as-code tooling. The workflow is widespread. The accuracy problem is still there.

## The specific limitation of a CI/CD pipeline

A docs-as-code pipeline can validate several things:

- Syntax: is the Markdown or MDX well-formed?
- Links: do the internal and external links resolve?
- Build: does the static site generator produce output without errors?
- Style: does the text pass a linter configured for your style guide?

It cannot validate whether a parameter name in a code sample still matches what the API actually accepts. It cannot detect that a field deprecated last sprint is still listed as required in the reference. It cannot tell you that the authentication flow in your getting-started guide was replaced by a new OAuth flow six weeks ago.

These are semantic questions. The pipeline has no access to what your API actually does. It only knows what your documentation says.

A CI/CD system that ships inaccurate content without error is doing its job correctly. The pipeline was never designed to catch semantic drift.

## Why the PR workflow assumption breaks

The standard docs-as-code recommendation is to tie documentation to pull requests: require a doc update alongside every code change. This is sensible in principle. It breaks in a specific way.

The developer writing the code change knows which feature was modified. They do not necessarily know which documentation pages are affected. A parameter rename might affect the API reference, a getting-started guide, a tutorial, two code samples, and a migration guide. The developer filing the PR will not know all of those surfaces.

Even when a PR template includes a "did you update the docs?" checkbox, the answer is limited by what the developer can see. They will update the page they know about. The page they do not know about stays inaccurate.

The problem is scope. Developers are not failing to do the work; they lack visibility into the full documentation surface. Documentation surfaces multiply faster than any individual contributor's mental model of them.

GitHub saw 986 million commits in 2025. Each commit is a potential documentation touch point that did not get followed up. At that velocity, the assumption that developers will catch their own documentation impact does not hold.

## What the numbers show

Teams that added change-detection monitoring on top of their docs-as-code workflows saw freshness improve from 38% of documentation reviewed in the last 90 days to 71%, according to the same 2026 report.

That is a 33-point jump without changing the writing workflow. The writing process stayed the same. The detection layer changed.

The difference: instead of depending on contributors to notice when documentation needed updating, a monitoring system watched for code changes and surfaced the documentation pages likely to be affected. Writers were routed to specific pages for review, rather than being asked to audit the entire corpus.

This is how software monitoring works. You do not audit your logs manually once a quarter to find errors. You set up alerting that surfaces anomalies in real time. Documentation accuracy has always needed the same approach; most teams have not applied it.

## The gap in your current setup

If you have docs-as-code in place, you have probably closed the workflow gaps. Documentation lives in version control. Engineers can contribute via PR. Deployment is automated. These are worth having.

The remaining gap: no signal connects what changed in your codebase to which documentation pages might now be wrong.

When a code change lands, your documentation system does not know it happened. Your writers do not receive a notification. The PR that introduced the change is merged and archived. Weeks later, a developer files a support ticket because the parameter name in the docs does not match what the API returns.

The chain that should connect "code changed" to "documentation reviewed" is not closed by the workflow. It requires a monitoring layer that watches code changes, maps them to affected documentation, and routes review tasks to writers.

The existing article on [documentation drift as a detection problem](/blog/technical/documentation-drift-detection-problem) goes into more detail on why manual approaches fail here. The short version: the signal exists in your PRs, commits, and release notes. The problem is that surfacing it manually does not scale.

That monitoring layer is what [Promptless](https://gopromptless.ai) is built to provide. It watches code changes and flags the documentation pages that need review, without requiring writers to track down what changed or engineers to remember which docs were affected.

The docs-as-code infrastructure is worth keeping. The accuracy problem it leaves open is also worth naming, so you know what to build next.
