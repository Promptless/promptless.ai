AI agents can write polished documentation, but they often miss what readers need to complete a task. That's the most common failure we found in [DoGBench (Documentation Generation Benchmark)](/blog/technical/dogbench), which we built with maintainers and technical writers from open source projects. In our audit of 1,267 submissions, 45.5% had a task-completion gap. Each of those patches omitted a decision point, procedure, verification step, or recovery path the reader needed. Invented classes, flags, and endpoints showed up in only 6.1% of submissions.

One Strawberry GraphQL patch correctly documented how to select an older Apollo Federation version. It never said why a reader would want to, which is to upgrade Strawberry while staying compatible with an older Apollo Router or Gateway. A reader with that upgrade problem can't tell this page solves it. It documented the setting and omitted the decision the setting exists to support.

## Polished writing can still leave readers unable to finish a task

Agents treat a change as one piece of information to convey, rather than one step in a journey that needs prerequisites, decisions, verification and recovery. A task-completion gap is a patch that drops one of those steps. The reader understands the feature and still can't finish the task that brought them to the page.

Two related failure modes cover the start of that journey. Missing prerequisites showed up in 21.0% of the 1,267 audited submissions. Missing audience and purpose framing, which leaves out who the content is for and when to use it, showed up in 19.9%. One patch can have several failure modes.

## Six of the seven agents never connected the workflow

On a public Azure Service Operator (ASO) item, six of the seven agents in the paper never connected the workflow the reader needed. An item is one real docs task, and you can [inspect this one on dogbench.ai](https://dogbench.ai/#item=Azure-azure-service-operator-pr5490&tab=rubrics), with every agent's patch and the rubric verdicts. A GitHub issue asked for this workflow:

1. Create a managed identity with ASO.
2. Export the identity's details to a Kubernetes Secret.
3. Point a resource's `credential-from` annotation at that Secret.
4. ASO then authenticates as the identity it created.

The rubric for this item checks for that workflow, connected end to end, on a page readers actually use. Here's how the seven agents in the paper did:

- Six of the seven documented a piece of the feature, such as a CEL helper function or a Secret-expression snippet. One said the exported Secret "can be used" with the annotation and stopped there.
- None of the seven fully covered the prerequisites, such as the permissions the managing credential needs to create the identity.
- None of the seven fully explained what the workflow is for and when to use it. The general CEL feature it's built on got the attention instead.
- Kimi K2.7 Code with OpenCode connected the steps, and its YAML passed the rubric's syntax criterion. Its example put both resources in one namespace and never said that ASO writes the exported Secret only in the managed resource's namespace. A reader who needs the identity in another namespace has to copy or mirror the Secret, and the patch doesn't tell them.

All seven patches had at least one critical defect on this item. Fluent prose makes these easy to miss, because the patch reads well and most of it is true.

## Agents have no model of how the product is actually used

Agents explain the interface without checking how readers use it. A trajectory is the record of an agent's steps. For each of the 1,267 submissions, we read the agent's trajectory and recorded the causes that the trace supports. The top three causes were:

- 36.0%, or 456 submissions, explained the changed fields, settings, or callbacks. They never tested that explanation against the reader's setup, decisions, steps, verification, or recovery.
- 33.1% stopped before the decisive evidence and filled the gap with a plausible assumption.
- 30.1% stopped at the first plausible page and left other affected pages stale.

That last cause reaches past the edited page. In the same audit, 20.7% of submissions put content where readers were unlikely to find it. Another 13.3% updated one page while a second page about the same behavior went stale. A patch can be accurate in isolation and still fail inside the documentation system.

The common thread is premature closure. Agents switch from investigating to drafting too soon, because they have no reliable rule for when they know enough. It isn't about effort. The root causes showed no clear link to trajectory length, in turns or in tokens. An agent can stop investigating early and still spend a lot of tokens drafting.

The reason a feature exists often lives outside the code. Nothing in the Strawberry change says a reader is stuck on an older Apollo Router. Documentation owners bring context that a code change alone may not reveal.

## Walk through the reader's whole task

Agents don't understand that a change is part of a larger workflow. Before you read a patch, write one sentence about who will land on the page and what they're trying to do. Then check the patch against that sentence with these prompts:

- Who is this for, and when would they use it?
- What has to be true first, such as permissions, credentials, or versions?
- Can the reader get from the first step to the last, on this page or through its links?
- How does the reader know it worked?
- What does the reader do when it doesn't work?
- Does each claim hold everywhere the text implies, including other defaults, versions, and namespaces?
- Will readers reach this page, and does another page about the same behavior need to change?

If the procedure is runnable, run it, or let a tool like [Doc Detective](https://doc-detective.com) run it for you.

If you configure docs agents, give them the same prompts before they draft. We tried prompts and skills like these only informally, so measure them on your own work.

## Promptless builds documentation agents, so we report its results separately

Two of the paper's authors work at Promptless, which builds documentation agents. Promptless's agent isn't one of the seven agents in the paper. It appears with the other cloud agents on dogbench.ai as a supplemental result. On the Azure Service Operator item, Promptless connected the workflow but missed the prerequisites and the namespace limitation. Its patch still had a critical defect.
