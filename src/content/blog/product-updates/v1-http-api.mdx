Promptless now has a versioned `/v1` HTTP API. Any HTTP client can submit documentation tasks, track their progress, read the suggestions feed, and send follow-up instructions. Authentication is a bearer token with a named API key.

## The problem

Triggering Promptless from code had one path: GitHub or GitLab webhooks. Merge a PR, Promptless picks it up from the event stream. That works for the common case. It does not work when you want to start a documentation task from a CI/CD pipeline, a deploy script, a cron job, or a Zapier automation watching an event Promptless doesn't natively handle.

There was an undocumented endpoint for submitting tasks, but it had no versioned contract and no way to read results. You could fire a task; you couldn't tell what Promptless did with it.

## What it does now

The `/v1` API has four surfaces.

**Submit a task.** `POST /v1/triggers` starts a documentation task. Authenticate with your `sk-pl-` API key as a bearer token. Pass an optional `Idempotency-Key` header and a retried request returns the original `trigger_event_id` instead of creating a duplicate. That matters when you're calling from a retry loop or a distributed system where the same event can fire more than once.

**Track a task.** `GET /v1/triggers/{trigger_event_id}` returns the current status of a submitted task, the full conversation Promptless had on it, and a summary of any suggestions it created, including docs PR links.

**Send a follow-up.** `POST /v1/triggers/{trigger_event_id}/messages` sends a follow-up instruction to a task, the same as typing a message in the dashboard conversation. Useful when you want to give Promptless additional context after it has already started working.

**Read the suggestions feed.** `GET /v1/suggestions` returns your organization's suggestions, each with its status, title, and docs PR link. Each suggestion carries a `trigger_event_id` field matching it to the task submission that produced it. An automation can submit a task, wait, then query the feed with that ID to find the resulting suggestion.

Doc collections are listable at `GET /v1/doc-collections`. The full OpenAPI spec is at `/openapi/api-triggers.yaml`.

## Who benefits most

Teams that want to start documentation tasks outside the GitHub or GitLab event stream. A deploy pipeline can submit a task after each release, poll for the resulting suggestion, and post the docs PR link to the relevant Slack thread or Jira ticket. A Zapier workflow can submit tasks in response to events Promptless doesn't watch natively, like a support ticket hitting a certain label or a Linear issue moving to a review column.

For teams running several automations in parallel, each caller can hold its own named API key. Keys are created and revoked independently. Revoking one does not affect others. Generating a new key no longer invalidates existing keys, which was the previous behavior.

## How to use it

Create a key from the API Triggers page in the dashboard. Name it for its caller, for example `release-pipeline` or `zapier-integration`. Each key is scoped to your organization and independent, so you can rotate one without interrupting any other.

Full endpoint reference, request/response schemas, and example payloads are in the [API triggers](/docs/for-docs/connect/triggers/api) guide.
