Here's a digest of four features we shipped recently, each with a docs page you can open to set it up.

## Promptless MCP server

**Start documentation tasks from the editor you already have open.**

Point an MCP-capable editor, such as Claude Code or Cursor, at the Promptless MCP server and hand off doc work mid-session, without switching to Slack, a GitHub comment, or the dashboard. You authorize once in the browser over OAuth, so there's no API key to create, store, or rotate, and the consent page names the organization you're connecting to before you approve. A `search_suggestions` tool lets your editor check for an existing draft before it starts a new task, so you don't create a duplicate. This is the interactive editor path, a companion to the API and CI trigger rather than a replacement for automation. See the [MCP triggers](/docs/for-docs/connect/triggers/mcp) page.

## Jira Done trigger

**Kick off a documentation review the moment a Jira issue reaches Done.**

Once Jira is connected and the trigger is configured, a status change into a done status can start a Promptless session, so no one has to remember to loop docs in when work wraps. Promptless works from the issue for context and then replies on the same ticket and attaches the documentation PR as a linked reference, so the outcome shows up where the work was tracked and routes through your configured publishing and notification policies. The done-status trigger is one of three configured Jira trigger types, alongside triggers for a new issue and a new label. Each type is named for the edge it fires on, so your configuration is explicit about when Promptless runs. See the [Jira](/docs/for-docs/connect/triggers/jira) page.

## Scheduled documentation checks

**Run a standing documentation check on your own clock, with no pull request or message required.**

Findings arrive as normal suggestions in your existing review queue and follow your configured publishing and notification policies, just like any other trigger. Write a standing instruction, then choose how often it runs, at most once an hour, and set the timezone. This works well for a narrow, recurring check on content that goes stale quickly, for example a Monday-morning check confirming your changelog and release notes still agree. It also suits a recurring drift sweep across a larger corpus, where nothing else would trigger a review on its own. See the [Schedule triggers](/docs/for-docs/connect/triggers/schedule) page.

## GitLab parity

**Drive Promptless from GitLab merge requests.**

Promptless picks up GitLab merge requests automatically when they're opened or updated. Connecting GitLab is a distinct, owner-level setup step: GitLab has no read-only app, so a group Owner creates a write-capable connection to switch it on. If you mention `@promptless` in a merge request comment, it adds a 👀 reaction so you know the request landed, even when it decides no doc change is needed. When you set up a new GitLab merge request trigger, you can replay recent MRs to run Promptless over merge requests from the last 30 days, which helps you calibrate before going live and catch up on anything missed. Promptless also posts a summary comment on the source merge request that links to the documentation changes it opened. See the [GitLab merge requests](/docs/for-docs/connect/triggers/gitlab-merge-requests) page.
